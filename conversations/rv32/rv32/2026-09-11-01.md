
这个 CLINT 接的是 NPC 的 `clk_i`，没有独立的 100 MHz 时钟输入。[连接代码](/home/yong/ysyx/ysyx-workbench-rv32-interview/npc/vsrc/riscv32/system/riscv32_npc_system.sv:107)

三个频率需要分开看：

| 项目 | 本次配置 |
|---|---|
| CPU 与本地 CLINT 共用时钟的建模频率 | 820 MHz |
| `mtime` 计数频率 | 1 MHz，即每 820 拍加 1 |
| AXI/APB 延迟模型采用的设备参考频率 | 100 MHz |

**最后这个 100 MHz，是设备延迟换算的参考值，不是一个独立驱动当前 CLINT 的时钟。** `820 MHz` 参数本身也不会生成新时钟，而是规定仿真周期代表多长时间，并据此设置分频和延迟。

> 定时器按每 820 拍增加 1 微秒运行；我们又拿周期数除以 820 MHz 做检查。两者一致，能验证采样、分频和统计窗口，却不能独立证明整个 SoC 的时间模型正确。

**你质疑这一点是有依据的。我之前把“统计内部一致”说得过于接近“性能时间已经全面验证”，需要收回这个强度。**

目前准确的说法是：

- **1.278899 秒**：当前模型假设下的计分时间。

## 0262 · 助手

**频率不一致当然可以算出时间，前提是明确每个计数器由哪个时钟驱动。你指出的是对的，我之前把“频率数值不同”直接说成错误，不够准确。**

CLINT 的计算关系是：

```text
实际时间 = mtime 增量 × 分频系数 ÷ CLINT 实际输入频率
```

因此：

- CLINT 真正由 **100 MHz** 驱动，每 **100 拍**加一，读数单位就是微秒。
- CLINT 真正由 **820 MHz** 驱动，每 **820 拍**加一，读数单位也还是微秒。
- CPU 是 820 MHz、CLINT 独立运行在 100 MHz，**完全没有问题**。

**我们的问题是，代码中 CLINT 与 CPU 接的是同一根时钟，而不是两个独立时钟。** `CLINT_CLOCK_FREQ_HZ` 只是用来计算分频系数的参数，它不会生成一个独立的 100 MHz 时钟。

旧代码相当于：

```text
每经过 100 个 CPU 时钟周期，mtime 加一；
软件将每个 mtime 增量解释为 1 微秒。
```

这个换算**在 CPU 按 100 MHz 建模时是正确的**。但如果同时声称 CPU 运行在 820 MHz，它就不正确了：

```text
100 个周期的实际时间 = 100 ÷ 820 MHz ≈ 0.122 微秒
软件却记录为                             1 微秒
```

此时报告时间会放大 **8.2 倍**。注意，这只是解释换算条件，**不能据此直接把旧的 4.92 秒除以 8.2，当成新成绩**，因为访存延迟对应的周期数也需要随频率调整。

所以，对旧数据更准确的判断是：

**旧的“计数转微秒”公式本身没有写错；它隐含了共享时钟为 100 MHz 的前提。错的是我们随后把这个时间，与另一频率下的 CPU 性能放在一起解释。**

对于 4.92 秒那次历史运行，目前能确认它符合 **100 MHz 换算口径**；不能仅凭这一点断言那次计时器算错了，也不能把它直接称为约 767 MHz 下的执行时间。我前面说“旧配置已经确认错了”，范围说得过大，应该纠正为：**旧成绩的频率归属和比较方式有问题，完整系统模型是否正确还要分别核查。**

当前系统需要区分两部分：

| 部分 | 包含什么 |
|---|---|
| CPU 的缓存设计 | I/D-cache 容量、相联度、命中延迟、缺失处理、回填与写回 |
| 外部访问的时序模型 | SDRAM 控制器及内存模型的响应时间、AXI/APB 延迟模块增加的等待时间 |

例如，假设外部内存的一次访问固定需要 **100 ns**：

- CPU 为 100 MHz，这段时间对应 **10 个 CPU 周期**。
- CPU 为 820 MHz，这段时间对应 **82 个 CPU 周期**。

**CPU 频率提高，外部内存不一定跟着变快，所以一次 Cache Miss 等待的 CPU 周期可能增加。** 这会降低 IPC；即使如此，执行时间仍可能缩短。

**你的方案完全成立：CLINT 如果确实接独立的 100 MHz 时钟，就应该一直按 100 MHz 换算，不需要知道 CPU 的频率。**

**但当前代码不是这样连接的。CLINT 和 CPU 接的是同一根时钟，没有给 CLINT 单独提供 100 MHz 时钟。** 我之前没有把这个事实讲清楚。

当前计时过程是：

1. 仿真器推进一个 CPU 时钟周期，CLINT 也同时收到一个周期。
2. 本次把这个共享时钟按 **820 MHz** 建模。
3. CLINT 每收到 **820 个周期**，让 `mtime` 加一。
4. 软件把 `mtime` 的增量直接作为微秒。

这里 `CLINT_CLOCK_FREQ_HZ=100000000` 或 `820000000` **只是用于计算分频的参数，不会改变接入的时钟，也不会产生独立时钟。**

你说的“按照 100 MHz 记录，最后也按 100 MHz 求时间”，分两种情况：

| 实际连接 | 是否成立 |
|---|---|
| CLINT 独立接 100 MHz，CPU 接另一个频率的时钟 | **成立**，CLINT 不需要知道 CPU 频率 |
| CLINT 与 CPU 共用按 820 MHz 建模的时钟，却把收到的周期按 100 MHz 换算 | **不成立**，计数的是 820 MHz 时钟的周期 |

因此，**当前方案需要 CPU 频率，是因为 CLINT 与 CPU 共用时钟；不是因为定时器在原理上必须依赖 CPU 频率。**

你提出的是另一种合理实现：为 CLINT 提供真正独立的 100 MHz 时钟，保持其计时基准不变。那样调整 CPU 频率时，就不应该再修改 CLINT 的分频参数。不过，仿真器也必须实际产生这两路频率不同、时间关系正确的时钟，不能只修改参数名称。

我查了修改前的 **`bb03677` 版本**。旧代码实际就是：**CPU 和 CLINT 共用时钟，每 100 个时钟周期让 `mtime` 加一，软件直接把这个增量当成微秒。**

**① 硬件参数写的是：**

```systemverilog
parameter int unsigned CLINT_CLOCK_FREQ_HZ = 100_000_000;
parameter int unsigned MTIME_INCREMENT_FREQ_HZ = 1_000_000;

localparam int unsigned CLINT_CLOCK_CYCLES_PER_MTIME_INCREMENT =
    CLINT_CLOCK_FREQ_HZ / MTIME_INCREMENT_FREQ_HZ; // 结果为 100
```

计数逻辑等价于下面这样，省略了复位等细节：

```systemverilog
// 每个 clk_i 上升沿更新
if (cycle_count == 99) begin
    cycle_count <= 0;
    mtime       <= mtime + 1;
end else begin
    cycle_count <= cycle_count + 1;
end
```

**② CLINT 接的就是系统共享时钟：**

```systemverilog
u_clint (
    .clk_i(clk_i),
    ...
);
```

CPU 也接这个 `clk_i`。**旧代码并没有另外生成一路 100 MHz 时钟给 CLINT。**

**③ 软件没有再除以频率，而是直接当微秒使用：**

```c
static uint64_t read_mtime_us(void) {
  uint32_t low  = *(volatile uint32_t *)0x02000048u;
  uint32_t high = *(volatile uint32_t *)0x0200004cu;
  return ((uint64_t)high << 32) | low;
}

void __am_timer_uptime(AM_TIMER_UPTIME_T *uptime) {
  uptime->us = read_mtime_us() - boot_time_us;
}
```

因此，旧代码实际上规定了：

```text
100 个共享时钟周期 = 1 微秒
```

**这就是按 100 MHz 建模的计时方式，本身可以成立。** 后来我将分频从 100 改成了 820，让它符合共享时钟按 820 MHz 建模的设置。

需要纠正我之前的表述：**旧代码不是“把独立 100 MHz 定时器算错了”，而是根本没有独立定时器时钟；旧成绩采用了共享时钟为 100 MHz 的时间解释。** 把它和另一频率下的结果直接比较，才是此前讨论中明确不严谨的地方。
