## 1206 · 助手

2026-09-28 14:31:25.718 UTC

**从第一版的功能划分看，确实接近把 CVA6 式 scoreboard 拆成“依赖与发射控制”和“按序完成队列”两部分。** 我们借鉴的是成熟结构，再适配现有 FU、异常和访存接口；不需要把它包装成新的算法。

CVA6 的 scoreboard 本身就包含在途指令管理、按编号接收结果和向提交级提供指令的功能。我们把其中的顺序管理独立命名为 ROB，是为了职责清楚，也便于以后接入重命名和乱序调度。[CVA6 官方说明](https://docs.openhwgroup.org/projects/cva6-user-manual/03_cva6_design/issue_stage.html)

**但这不意味着必须变成六级，更不意味着再额外加一级 issue 或 commit。**

CVA6 官方描述的六级是：

**PC 生成 → 取指 → 译码 → 发射 → 执行 → 提交**

其中已经包含 issue 和 commit，并不是六级之外再加它们。[官方结构说明](https://docs.openhwgroup.org/projects/cva6-user-manual/07_cv32a60x/design/design.html)

对我们的实现，我准备按下面的原则处理：

| 部分 | 初步安排 |
|---|---|
| 译码、scoreboard 检查、读寄存器和前递选择 | 优先放在现有执行入口寄存器之前，不默认增加独立 issue 寄存级 |
| FU 接收与执行 | 接收后自行保存操作数和身份，长除法不再一直占住公共 ID/EX |
| ROB | 发射时分配条目，完成时按编号填写结果；不是让指令额外经过一个固定延迟的执行级 |
| Commit | 从 ROB 队首判断能否退休，优先由 ROB 承担原 WB 的结果保存职责，不再机械串接一套 WB 和 commit 寄存器 |

**现有 `riscv32_commit` 本来就是组合逻辑，没有独立流水寄存器。** 当前是 WB 寄存器保存结果，commit 根据它生成架构更新信号。[当前流水说明](/home/yong/ysyx/ysyx-workbench-rv32-interview/npc/docs/microarchitecture/PIPELINE_DESIGN_RECORD.md)

另外，**ROB 有四项，不代表指令要多经过四拍**。条目数量决定可以保存多少条在途指令；一条指令什么时候退休，取决于它是否完成、是否位于队首，以及副作用是否允许提交。

所以，这次设计先确定寄存器边界和握手关系，**不预先规定“必须六级”**。若依赖检查与操作数选择确实成为关键路径，再根据 STA 和程序执行时间决定是否拆出独立 issue 级；不能因为模块名字增加了，就给每个模块加一拍。

## 1209 · 助手

2026-09-28 14:44:41.390 UTC

**CVA6 独立设置 issue 级有明确的电路理由；我们是否需要同样拆分，应该由新增 scoreboard 后的关键路径决定。目前我倾向先合并实现，再把独立 issue 级作为对照方案。**

CVA6 的译码先产生指令控制信息，并将它寄存；下一拍的 issue 主要完成：

- 检查源操作数是否就绪、目的寄存器是否冲突。
- 检查目标 FU 是否能够接收。
- 读取寄存器、选择前递数据，将操作数送往 FU。

这些操作本身就有比较器、选择器和控制扇出。**把它们与指令译码分开，可以缩短单拍组合路径，也给受阻指令提供稳定的保存边界。** 这是根据其 RTL 划分得到的电路解释；并不意味着 scoreboard 在功能上必须独占一拍。[CVA6 发射说明](https://docs.openhwgroup.org/projects/cva6-user-manual/03_cva6_design/issue_stage.html)、[译码输出寄存器](https://github.com/openhwgroup/cva6/blob/master/core/id_stage.sv)

我们当前的级数，需要明确统计条件。**按 I-cache 命中、缓冲为空、无停顿的普通 ALU 最短路径，可以划分为六个时钟阶段：**

| 阶段 | 这一拍完成什么 | 拍末保存在哪里 |
|---|---|---|
| 1 | PC 对应的预测查询 | 预测响应寄存器 |
| 2 | 发起 I-cache 查询、同步读取阵列 | I-cache 请求及阵列读出寄存器 |
| 3 | 命中选择、译码、读寄存器、依赖检查与前递 | ID/EX |
| 4 | ALU 执行 | EX 结果寄存器 |
| 5 | 结果处理与完成仲裁 | WB |
| 6 | 提交，更新架构状态 | GPR、CSR 等架构寄存器 |

这里有三个限定：

- 请求队列和 fetch buffer **空闲时直通，不固定增加一拍**。
- LSU、三拍乘法和迭代除法走不同执行路径，不能认为所有指令都是六拍。
- 我之前说 commit 是组合逻辑，指的是 **commit 模块内部没有再加寄存器**。WB 输出到架构寄存器更新之间，仍然可以称为提交阶段。[当前流水说明](/home/yong/ysyx/ysyx-workbench-rv32-interview/npc/docs/microarchitecture/PIPELINE_DESIGN_RECORD.md)

**我们现在确实把较多工作放在第三阶段。** 增加 scoreboard 后，这条路径可能变成：

`I-cache 命中选择 → 译码 → ROB/依赖查询 → 前递选择 → FU 入口`

因此，独立 issue 级值得评估，不能事先认定它一定多余。但也不能直接认定必须增加：

1. 小容量 ROB 的依赖查询，可能替代目前较复杂的多级生产者比较，未必一定更慢。
2. 当前 700 MHz 的最差路径主要经过 LSU 完成与 ready 控制，并非已经证明译码、寄存器读取过长。
3. 加 issue 寄存级会增加指令延迟，并可能推迟分支解析；稳定吞吐仍可保持每拍一条。
4. **普通弹性寄存器不一定截断反向 ready 路径**，所以加一拍未必解决真正的关键路径。

我的实施原则是：**先保留合并的译码/发射，完成小 ROB 和依赖控制；若 STA 证明这部分成为主要瓶颈，再拆独立 issue，并比较面积和实际执行时间。** 同时重新审视原有 EX 结果级、WB 与 ROB 的职责，避免只在现有流水线上不断追加寄存级。

**不一定必须增加 issue 级，但现在确实有评估这一级的理由。** 关键是切断实际的长组合路径；只增加一个流水级名称或寄存器，不能保证达到 700 MHz。

我刚用**当前 4 项 ROB、开启 load overlap 的同一份综合网表**补跑了 700 MHz STA：

| 频率 | 最差数据 setup 余量 | 最差门控 setup 余量 |
|---|---:|---:|
| 600 MHz | +30 ps | +21 ps |
| 620 MHz | −13 ps | −22 ps |
| 700 MHz | **−160 ps** | **−169 ps** |

Hold 检查通过。具体见 [700 MHz 报告](/home/yong/ysyx/ysyx-workbench-rv32-interview/npc/result/backend-rob/sta700-audit-20260929/riscv32_core_reset_boundary.rpt)。

**第一条关键路径终止于 ROB 条目的写入端：**

指令 AXI `RVALID` → I-cache 回填响应选择 → fetch buffer 空队列直通 → 译码 → scoreboard 的生产者匹配、年龄选择与就绪判断 → 入队许可 → ROB 条目写入。

对应的[入队控制](/home/yong/ysyx/ysyx-workbench-rv32-interview/npc/vsrc/riscv32/core/execute/riscv32_backend.sv:148)同时考虑操作数是否就绪、ROB 空间、ID/EX 接收能力以及恢复条件。**目前这些判断与前面的取指、译码逻辑处于同一个组合路径中。**

加入 ROB 后，新增了按年龄选择结果版本和队列分配条件，原来的寄存边界因此承受了更多逻辑。

**第二条关键路径终止于 I-cache 替换状态的门控使能：**

上述接收条件继续通过 fetch buffer 的 `ready` 反馈，影响 I-cache RRIP 状态的更新使能。因此，不能仅因为终点在 I-cache，就把问题全部归因于替换算法。

我建议按下面的顺序处理：

1. **先尝试不加级的电路优化。** 缩短 scoreboard 的最近生产者选择与就绪判断，减少入队使能的串联条件和扇出。能否省下约 160～170 ps，需要综合验证。
2. **如果仍不足，再试译码与 issue 之间的寄存边界。** 让译码结果先寄存，下一拍完成依赖检查、操作数选择和 ROB 分配，保留现有进入执行单元的寄存边界。同时检查 `ready` 反馈，避免数据路径切开后，反压路径仍然贯通。

这里有一个重要限制：**为了截断时序而增加的寄存边界，不能又通过“空时直通”把同一条关键组合路径接回来。** FU 结果前递、队列同拍出入等旁路仍应保留，但需要明确它们跨越哪些电路边界。

增加 issue 级可以保持每拍发射一条的吞吐，但会增加指令延迟，也可能增加分支恢复代价。因此，应比较最终执行时间与面积，不能仅凭达到 700 MHz 就认定方案更好。
