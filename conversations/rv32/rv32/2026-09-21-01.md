## 0531 · 助手

2026-09-21 04:22:31.783 UTC

**还有可优化的等待，也有源码冗余；代码风格尚未全部达到你的要求。** 本轮重新检查了当前 RV32 的 **45 个硬件模块、5 个 package**，并核对了仿真模块和历史实验的用途。

主要发现如下：

| 位置 | 现有问题 | 判断 |
|---|---|---|
| D-cache 脏行采集 | 最后一字已经返回，下一拍才发写回请求 | 已仿真确认，可尝试末字旁路 |
| D-cache 脏行 miss | 写回请求被接收后，下一拍才发 refill，读通道空闲也等待 | 已仿真确认，可尝试同拍启动 |
| I/D-cache miss 完成 | 完成当拍仍不接受下一查询 | 需要补齐回填安装与同步读取之间的旁路，不能只放宽 ready |
| FENCE.I | 前端已空闲仍经过 drain；clean 完成后下一拍才发 invalidate | 已仿真确认，可研究条件满足时直接交接 |

**这些是优化候选，还没有证明改完后整体更优。** 增加 bypass 可能增加选择器和组合路径，仍须比较面积、时序及实际程序周期。

源码和风格方面，明确还有：

- **重复接线**：删除流水级后，`core` 仍保留两套译码信号别名；I-cache 元数据也有不再承担选择功能的中间接线。
- **顺序不够直观**：I/D-cache 先实例化阵列，数百行之后才计算阵列输入；CLINT 的写控制与寄存器更新相隔较远。
- **过时注释**：I-cache 仍写着已经删除的“invalidate 状态机”，部分位置仍描述旧的寄存重定向。
- **重复表达式和辅助函数**：字节合并、数据移位等可以整理，但不能直接认定综合后也有重复硬件。

状态机大体遵守了“**输出逻辑 → 下一状态 → 寄存器更新**”，但整个文件还没有都做到沿实际电路连接顺序阅读。后续应优先整理局部电路的依赖关系，而不只是调整排版。

本轮 **24 个 D-cache miss 用例全部通过**，另用 FENCE.I 探针确认了上述交接等待。CPU RTL 未修改，没有新的面积或 IPC 成绩。

逐模块结论、具体取舍和验证记录已写入[复查文档](/home/yong/ysyx/ysyx-workbench-rv32-interview/npc/docs/verification/RV32_LOGIC_STYLE_AUDIT_2026-09-21.md)。

## 0536 · 助手

2026-09-21 04:37:42.910 UTC

**值得继续优化，但应分清优先级，不能把“能加 bypass”直接当成“应该加”。**

结合当前 train 计数，我的判断是：

| 项目 | 建议 |
|---|---|
| 重复接线、过时注释、重复表达式、源码顺序 | **优先整理**，可读性收益明确 |
| D-cache 写回与 refill 同拍交接 | **优先做小规模实验**，主要调整已有控制 |
| 最后一个脏行字直接旁路到写回 | 随后独立尝试，避免为一拍收益增加过多选择逻辑 |
| I-cache 完成时接收下一查询 | 先统计实际触发次数，再评估同址旁路成本 |
| D-cache 完成时接收下一查询 | 优先级较低，现有可见请求等待占比很小 |
| FENCE.I、串行化交接 | 暂缓；当前 train 的 FENCE.I 位于启动段，串行化优化涉及更多正确性边界 |

例如，前两处脏行交接若每次各省一拍，按当前数据理想估算合计约 **2.35 ms、0.14%**。这还不是实测收益，不值得为此付出明显的面积增长或执行时间退步。详细依据已补入[优化取舍记录](/home/yong/ysyx/ysyx-workbench-rv32-interview/npc/docs/verification/RV32_LOGIC_STYLE_AUDIT_2026-09-21.md:24)。

**设计规范已经更新，并规定每次 RTL 设计、修改和评审都参考：**

- 每组寄存器、每个等待必须有明确的电路理由。
- 检查空缓冲直通、同拍出入、最后响应直接完成、前递和阶段交接。
- bypass 必须同时处理数据、身份、反压、异常及同址冲突。
- 结合周期数、面积、通过时序的频率和维护成本决定是否保留。
- 源码按实际数据流组织；FSM 保持“输出 → 次态 → 寄存器更新”，同步清理旧描述。

正文集中在[编码规范](/home/yong/ysyx/ysyx-workbench-rv32-interview/npc/docs/development/NAMING_GUIDE.md:76)。新增的简短 [AGENTS.md](/home/yong/ysyx/ysyx-workbench-rv32-interview/npc/AGENTS.md)只作为阅读入口，不重复维护规则。

## 0594 · 用户

2026-09-21 10:10:28.212 UTC

1. 高优先级：FENCE.I 之后可能保留旧的 taken 预测，且非分支指令无法纠错
   这是本轮最需要补定向仿真的问题。已有具体源码路径支持，但我尚未通过 RTL 仿真复现。
   问题并不是“FENCE.I 必须清空所有预测器”。规范要求的是同一 hart 后续取指正确观察之前的代码写入；实现可以保留某些预测状态，但错误预测必须能够被识别和恢复。RISC-V 文档
   当前代码中，下面几个行为组合起来形成了风险：
   环节	当前源码行为
   FENCE.I 提交	当拍发起 redirect，恢复地址为 commit.next\_pc
   缓存维护期间	暂停向 I-cache 发出新的取指访问，但没有同步暂停预测查询
   预测器失效	到后面的 I-cache invalidate 阶段，才通过 invalidate\_i 清理 BTB/RAS
   已生成的预测	预测响应寄存器、IFU 请求队列中的预测，并不会因为表项失效而自动清除

这些连接分别位于 riscv32\_fence\_i\_ctrl.sv、riscv32\_core.sv、riscv32\_ifu.sv 和 riscv32\_branch\_predictor.sv。尤其是，预测器响应流水的清除条件是 flush\_lookup\_i，而 IFU 当前把它接成 redirect；维护完成时没有第二次前端恢复。
由此可以构造这样的执行过程：

1. 地址 A 原来是 jal x0, T，已经在 BTB 中训练出 taken 预测。
2. 软件把 A 修改成 addi 或 nop，随后执行 FENCE.I，让 A 成为维护后首先执行的地址。
3. FENCE.I 已经触发初始 redirect，但 D-cache 仍在 clean。此时预测器可以使用尚未失效的 BTB，把 A → T 的旧预测放入新的取指请求队列。
4. 缓存维护完成后，I-cache 返回 A 的新指令，但与它配对的预测仍可能是旧的 taken 预测。
   这本来应该只是一次需要纠正的预测错误。然而当前 riscv32\_ex\_result\_reg.sv 的纠错条件明确要求：
   if ((execute\_result\_q.uop.fu\_type == FU\_BRANCH) &&
   !execute\_result\_q.uop.exception\_valid &&
   branch\_prediction\_mismatch) begin
   resolved\_result\_o.redirect\_valid = 1'b1;
   end
   如果 A 已经变成普通整数指令，它不会进入这个纠错条件。 因而存在新指令本身执行正确，但后续继续沿旧目标 T 执行、跳过 A+4 的风险。若改成 load/store，还必须考虑 LSU 路径不经过普通 EX 结果寄存器的问题。
   这也说明：仅测试“旧分支改成另一个分支”不够，必须测试“旧分支改成非分支”。
   我的建议是从两个层面处理：
   维护协议层面，明确维护完成前允许生成哪些预测，以及哪些预测可以在完成后继续使用。可以暂停维护期间的预测并在完成后启动，或者在维护结束时重新恢复前端、清除维护前产生的预测快照。无论采用哪种方案，都不能直接撤销已经展示且受阻的 I-cache 请求，仍需遵守现有握手和旧 epoch 排空规则。
   错误恢复层面，增加“BTB 预测为跳转，但实际指令不是控制流指令”的纠错能力。仅删除上述 FU\_BRANCH 判断还不完整，因为 load/store 不经过这一结果级；需要在覆盖所有相关指令的边界处理。
   最小定向测试应检查的不是最终程序是否结束，而是：修改后的 A 提交后，下一条应提交 A+4，错误目标不得产生 store 或 MMIO 副作用。
5. 总线错误处理缺口：FENCE.I 的 clean 失败后仍可能继续恢复执行
   这项问题的源码连接比较明确，触发条件是 D-cache clean 写回收到错误响应，不属于正常无错误总线路径。
   当前 D-cache 在 clean 写回失败时能够给出：
   clean\_done = 1
   clean\_access\_fault = 1
   但 riscv32\_fence\_i\_ctrl 只接收 dcache\_clean\_done\_i，没有错误输入。因此它仍会继续进入 I-cache invalidate，随后结束维护。核心对 dcache\_clean\_access\_fault 的处理，是 ifndef SYNTHESIS 下的断言，而不是实际硬件异常或停止机制。
   仿真中的 $error 不等于芯片中的错误恢复。 如果 dirty code 没有成功写回下层，清掉 I-cache 后重新取指，也不能保证取到正确的新代码。
   这里需要先定义系统策略：

- 要支持可恢复的维护错误，就需要保存足够的维护上下文，并规定错误如何向软件报告、是否允许重试。
- 要把这种错误视为不可恢复，就需要实际的 fatal/error 状态或系统级错误通知，不能继续按成功维护处理。
  还有一个必须注意的架构边界：当前 FENCE.I 在启动维护前已经经过 commit。 因此，不能简单在若干周期后补一个“属于这条 FENCE.I 的普通精确异常”，而不重新规定其退休与维护完成的关系。

3. 总线错误恢复边界：脏行替换失败后，没有保留可恢复的旧数据状态
   当前普通 dirty miss 可以在写回 B 响应尚未完成时启动新行回填。新行安装前会检查相关响应是否成功，这一点已经处理；但它与“旧脏行可以恢复”是两件事。
   当前路径是：
   保存 victim 数据
   → 发起写回
   → 使旧行失效并回填新数据
   → 若写回失败，向当前访存返回 access\_fault
   → 结束本次 miss
   我没有在这条状态机中看到写回失败后的 victim 恢复、重新安装或受保护重试路径。虽然 victim\_line\_data\_q 中可能还暂时留有数据，但事务结束后，没有独立的恢复状态保证它不会被下一次 miss 覆盖。
   问题在于，旧脏行可能包含已经退休的 store。当下层没有成功保存完整脏行时，给“当前触发替换的 load/store”返回异常，并不能自动恢复那些老 store 的数据。
   因此，我会把这一点表述为：
   当前具备写回错误检测和访存错误返回，但不能据此认为已经具备可恢复的脏行写回失败处理。

如果系统规定这类错误不可恢复，需要把该规定落实到硬件行为；如果要求软件能够继续运行，则必须延长 victim 的保护生命周期，并设计恢复或重试协议。这不是要求所有总线错误都能回滚，而是要求错误后的架构状态和允许继续执行的条件有明确约定。
