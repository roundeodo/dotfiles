## 0215 · 助手

2026-09-06 14:07:13.173 UTC

**用定时器外设统计执行时间完全可以，而且当前就是这样做的。问题不在这种方法，而在于此前定时器的分频、访存延迟比例和所宣称的 CPU 频率没有统一。我之前没有把这一点解释清楚。**

当前实际有两套测量：

| 统计内容 | 实际读取的数据 | 计算方法 |
|---|---|---|
| IPC | CPU 的 `mcycle`、`minstret` | 退休指令增量 ÷ CPU 周期增量 |
| 执行时间 | 内存映射定时器 `mtime` | 定时器计数增量 ÷ 定时器计数频率 |

**IPC 本身不需要知道 CPU 是多少 MHz。** CPU 等待缓存、总线、数据依赖时，周期仍应计入；指令数则统计退休指令，不能统计取指或译码次数。多个子测试的整体 IPC，应当用“指令总增量 ÷ 周期总增量”，不能直接平均各子测试的 IPC。

当前 MicroBench 就是在各个 `run()` 前后读取这两个 CSR，累加差值。RV32 下还使用“高—低—高”读取避免跨 32 位进位读错。不过，两种 CSR 是依次读取的，包含少量测量开销，并非同一时刻的原子快照。

**程序的时间也确实来自硬件定时器。** 更准确地说，程序通过 AM 读取 `0x02000048/4c`，实际访问的是我们在 NPC 系统层实现的 CLINT。代码在 [timer.c](/home/yong/ysyx/ysyx-workbench-rv32-interview/abstract-machine/am/src/riscv/ysyxsoc/timer.c)。

关键在于：**这个 CLINT 使用 CPU 时钟分频，没有独立时钟源。**

- CPU 按 100 MHz 模拟时，每 **100 拍**增加一次 `mtime`，才表示经过 **1 微秒**。
- CPU 按 820 MHz 模拟时，每 **820 拍**增加一次，才仍然表示 **1 微秒**。

如果是由独立稳定时钟驱动的定时器，CPU 变频通常不需要修改它的时间换算；我们的实现需要同步调整分频。

“访存模型变化”则是另一件事：外设按 100 MHz 建模，CPU 按 820 MHz 建模，设备响应时间就需要折算为相应数量的 CPU 周期。原来的延迟比例约 **2.966**，后来改为约 **8.2**。**这会改变程序等待访存的周期数，因此会改变 IPC；仅修改定时器分频则不会让普通计算突然少执行周期。**

此前的配置是：

> 定时器按 100 MHz 换算，访存延迟却按约 296.6 MHz CPU 配置，再拿 820 MHz 的 STA 结果介绍性能。

这三者不一致，所以不能把原来的 **6.533 秒**直接解释为 820 MHz 下的执行时间。

现在明确配置为 CPU 820 MHz、设备 100 MHz 后，完整 train 的结果可以交叉核对：

- PMU 周期：**1,089,343,319**
- 按 820 MHz 换算的 PMU 窗口时间：**1.328467 秒**
- 定时器测得的 `Scored time`：**1.328498 秒**

2026-09-06 14:13:28.603 UTC

**是的，读 CSR 有额外开销。当前这些读取是在被测 CPU 上执行的，不是宿主仿真软件在外面直接取数。这个区别必须明确。**

我检查了实际 ELF：`read_pmu_snapshot()` 包含 **6 条 CSR 读取、2 条条件分支、4 条存储和一条返回指令**，外面还有调用指令。每个子测试前后各调用一次。读定时器的 MMIO 指令也同样有开销。

因此，当前程序实际上执行的是：

```text
准备数据
读取开始时间
读取开始 CSR 快照
执行 run()
读取结束 CSR 快照
汇总统计
读取结束时间
校验结果
```

**目前测到的是带测量代码的程序，不能称为原始 workload 的无开销测量。** 而且不能简单减去固定几拍：当前 CSR 指令会串行化，额外调用、存储和代码布局还可能改变流水线、缓存及预测状态。影响有多大，需要对照实验，不能凭感觉忽略。

要把执行时间和 IPC 统计清楚，我认为应明确采用下面的规则。

**第一，先固定 workload 的边界。**

针对我们一直比较的 MicroBench 计分部分，统计十个 `run()` 的动态执行，包括它们调用的函数，排除准备和校验。可以让仿真器根据实际 ELF 中的调用与返回事件识别边界：

- 外层 `run()` 调用指令退休后打开窗口。
- 外层返回指令退休所在拍计数完成后关闭窗口。
- 内部函数调用、返回不能误开关窗口。

这是明确的“退休边界窗口”。如果关心包含启动、准备、校验和打印的完整程序时间，就另设从复位释放到正常退出的窗口，不能与它混用。

**第二，在仿真环境里，对同一个窗口同步统计周期和退休指令。**

窗口开启期间：

- 每经过一个 CPU 周期，`C += 1`，包括访存等待、流水停顿和没有退休指令的周期。
- 每退休一条有效指令，`N += 1`。不能用取指数、发射数替代，也不能把异常指令算作正常退休。

然后：

\[
IPC=\frac{\sum N}{\sum C},\qquad
执行时间=\frac{\sum C}{f_{\mathrm{CPU}}}
\]

这样 **IPC 和执行时间使用完全相同的周期窗口**。当前选择 820 MHz，就使用 820 MHz，并保持对应的访存延迟配置。

仿真器观察这些信号、累计宿主变量，**不会向被测 CPU 插入指令或增加 CPU 周期**，只可能使宿主仿真跑得更慢。

**定时器仍然可以使用。** 软件测时本来就允许存在测量开销；`Δmtime / 定时器频率` 是正确方法。但若目标是分析不受附加测量代码影响的硬件性能，就应以仿真旁路统计为主，定时器作为交叉检查。

这里也纠正一下此前结果的定位：**0.171489 IPC、1.328498 秒属于现有插桩镜像的测量结果，尚不是上述无附加 PMU 插桩、严格同窗统计的结果。** 现有仿真监视器只是旁路观察了插桩程序，并没有消除插桩开销。

我已把这些边界和后续统计协议写进[计时说明](/home/yong/ysyx/ysyx-workbench-rv32-interview/npc/docs/verification/MICROBENCH_TIMING_RULES.md)。新协议尚未实现重跑，不能拿旧数字直接替代它的结果。

## 0223 · 助手

2026-09-06 14:25:49.306 UTC

重新考虑后，我认为应该采用：**保留 MicroBench 原本的计时方式，去掉我们额外加入的 CSR 插桩，由仿真环境只读观察周期、指令退休和定时器采样事件。**

关键不只是少执行几条测量指令，还要确保：**执行时间和 IPC 对应同一个区间，统计本身不改变 CPU 的执行。**

目前我完成了代码核对和方案修订，尚未接入新的统计器，也没有产生新的测试成绩。

**1. 保留基准原有的开销，去掉我们额外添加的开销**

MicroBench 原版就在每项测试前后读取定时器。这些读取属于基准原有的执行流程，应该保留，否则测试定义就变了。

我们后来加入的 `mcycle/minstret` 快照则不同：它们确实是被测 CPU 执行的 CSR 指令，还带有分支、存储和调用开销。它们也可能改变代码布局、Cache 和预测器行为，因此不能简单减去一个固定周期数。

后续默认性能测试应恢复原有测量流程，把这些额外快照保留为可选诊断方式。

**2. 在仿真侧统计，不让 CPU 执行额外的统计指令**

仿真环境持续维护两个计数：

- **周期数 C**：每个 CPU 周期计一次，包含 Cache Miss、访存等待、流水线停顿和重定向等开销。
- **退休指令数 N**：只统计真正退休的指令，不能按取指、发射或所有 `commit_valid` 直接累计。

这里确实需要修正现有统计入口：当前 `commit_valid` 可以包含发生异常的提交，不能直接等同于 `minstret` 的退休口径。

仿真侧观察内部信号不需要执行 `csrr`，也不应驱动任何流水线控制信号。它可能让宿主机仿真变慢，但不应增加被测 CPU 的周期。官方一生一芯文档也支持在仿真中统计动态指令数和周期数来计算 IPC。[官方说明](https://ysyx.oscc.cc/docs/2407/b/4.html)

**3. 时间和 IPC 必须使用同一对起止事件**

这是此次重新考虑后最重要的修正。

之前提出用“进入 `run()`、退出 `run()`”划定区间，适合分析函数，但**不能直接替代 MicroBench 原本的计分窗口**。

当前 CLINT 在接受 `mtime` 低字读地址时保存时间快照。这个采样时刻，与读响应返回、读取指令退休可能相差多个周期。

因此，应该在原生定时器真正采样时，同时由仿真侧保存：

```text
开始：(C0, N0, mtime0)
结束：(C1, N1, mtime1)

区间周期数 = C1 − C0
区间退休数 = N1 − N0
IPC        = 区间退休数 / 区间周期数
执行时间   = 区间周期数 / CPU 频率
```

计数与快照必须遵守同一种时钟边沿约定。多个子测试的总体 IPC 应计算为 **Σ退休数 / Σ周期数**，不能直接平均各项 IPC。

还要根据实际程序调用上下文识别哪些定时器读取属于计分，不能简单地每两次读取配成一组：初始化和整个程序计时也会读取定时器。

**4. 三类结果分别报告**

| 指标 | 测量区间 | 用途 |
|---|---|---|
| 基准计分时间与 IPC | 原生计分定时器的起止采样 | 作为主要性能结果 |
| 完整程序时间与 IPC | 释放复位至程序正常退出 | 衡量启动、准备、验证、输出等整体成本 |
| 函数区间统计 | 明确定义的函数调用与返回边界 | 定位具体瓶颈 |

MicroBench 输出的 `Total time` 也有自己的程序内边界，不能直接当成“释放复位至退出”。

**5. 用对照实验证明低侵入**

同一个仿真器、同一个程序镜像，通过运行时开关启用或关闭观察器，比较：

- 程序结果和退出状态；
- 架构状态及访存副作用；
- 最终执行周期数。

这些应当一致。统计代码还应限制在仿真侧，避免进入综合、增加实际硬件面积。先用短程序验证异常、停顿和计时边界，再运行 MicroBench test，最后重跑 train。

比较不同 CPU 方案时，还必须固定镜像、频率、访存延迟、初始状态和中断配置。**低侵入解决测量扰动，不能代替对 SoC 时序模型的校准。**

方案已经写入 [MICROBENCH_TIMING_RULES.md](/home/yong/ysyx/ysyx-workbench-rv32-interview/npc/docs/verification/MICROBENCH_TIMING_RULES.md:156)。之前的成绩仍然是带 CSR 插桩版本的有效测量，同镜像下的优化对比仍有意义；恢复原版流程后，需要建立新的基线，不能把旧成绩直接改称“无额外插桩的性能”。
