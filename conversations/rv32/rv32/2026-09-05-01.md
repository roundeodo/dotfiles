## 0006 · 助手

2026-09-05 18:15:40.394 UTC

**这个设定作为长期研究方向是合理的，但目前文档还不足以证明所规划的 CPU 微架构适合目标负载。** 我建议把定位明确为：

> **面向本地 AI 推理异构 SoC 的 RV64 通用处理器核，重点研究系统软件、标量处理和加速器协同的性能与能效。**

我阅读了架构计划、工作负载模型、流水线、缓存、互连和验证文档，并核对了配置源码。下面区分方向本身与现有规划的问题。

**首先，你的文档实际面向的是较高性能的本地推理设备。**

[工作负载模型](/home/yong/ysyx/ysyx-workbench/npc/docs/architecture/AI_WORKLOAD_MODEL.md:9)明确选择了 AI PC、个人工作站和紧凑型推理节点，第一阶段模型规模是 3B～14B。

这个场景成立，但“边缘设备”不足以表达它的资源要求。低功耗传感器上的关键词识别，与工作站上的量化语言模型，在内存容量、操作系统和计算需求上差别很大。MLCommons 也分别设置了面向微小设备的 [MLPerf Tiny](https://mlcommons.org/benchmarks/inference-tiny/) 和面向本地生成式 AI 的 [MLPerf Client](https://mlcommons.org/benchmarks/client/)。

因此，应进一步固定一种首要设备。**AI PC、工作站和紧凑节点可以作为应用范围，首版设计需要一个明确的功耗、内存和性能预算。**

**其次，CPU 与加速器的分工基本合理，但“AI 推理 CPU”容易让人误解计算职责。**

[现有分工](/home/yong/ysyx/ysyx-workbench/npc/docs/architecture/AI_WORKLOAD_MODEL.md:57)让 CPU 执行操作系统、runtime、地址计算、部分前后处理和命令提交，让向量或矩阵单元处理主要张量计算。这是有工程依据的组织方式，例如 [Ara](https://github.com/pulp-platform/ara) 就采用 CVA6 标量核与 RVV 向量协处理器组合。

这个定位下，CPU 的价值应通过具体问题证明：

- CPU 提交任务不够及时，是否造成加速器等待？
- 数据整理和小算子是否显著增加推理延迟？
- CPU 与 DMA 的数据共享是否引入大量复制、缓存维护和同步？
- 加强 CPU 后，整机任务时间与每次推理能耗改善了多少？

**CPU 更快不必然意味着推理系统明显更快。** 例如，假设 CPU 上可优化的串行工作占总延迟的 10%，将这部分速度提升一倍，总体加速只有：

\[
\frac{1}{0.9+0.1/2}\approx1.053
\]

即约 5.3%。这是说明评价方法的假设计算，并非本项目测量结果。

文档中“CPU 不能长期空闲”的表述也建议调整：CPU 在完成提交后等待加速器，可能正是合理运行状态。应该追求任务及时完成和系统能效，而非 CPU 持续忙碌。

**目前最需要修改的是：把乱序和超标量提前确定成了产品必需条件。**

[架构路线](/home/yong/ysyx/ysyx-workbench/npc/docs/architecture/ARCHITECTURE_PLAN.md:103)安排为：

`顺序核 → 单发射乱序 → 超标量乱序 → AI 异构扩展`

作为学习高性能 CPU 的路线，这样逐步增加复杂度很合理。但作为面向 AI 的产品路线，它会让关键的负载验证发生得太晚。

而且，文档同时规定“先证明瓶颈，再增加资源”。尚未测量 CPU 对推理任务的限制，就固定超标量乱序为必经阶段，与这条原则存在张力。

顺序核也能承担应用处理器和向量协同职责。[CVA6 官方说明](https://github.com/openhwgroup/cva6)描述了单发射顺序执行、虚拟内存和 Unix 类操作系统支持；Ara 则提供了与它结合的实例。这支持的结论是：**乱序并非建立 AI 推理系统的前提，其收益需要针对负载测量。**

如果你的主要学习目标就是乱序 CPU，完全可以保留这个目标。文档应明确“用于学习和研究乱序机制”，同时把“改善 AI 系统性能”列为待验证假设。

**更具体的缺口在内存容量、带宽和软件能力上。**

单看量化权重，按参数数量乘以每参数存储位数计算：

| 参数规模 | INT4 权重理论体积 | INT8 权重理论体积 |
|---|---:|---:|
| 3B | 1.5 GB | 3 GB |
| 7B | 3.5 GB | 7 GB |
| 14B | 7 GB | 14 GB |

这里使用十进制 GB，尚未计入量化元数据、KV cache、激活、运行时和操作系统。

我核对的[配置源码](/home/yong/ysyx/ysyx-workbench/npc/vsrc/riscv32/common/riscv_config_pkg.sv:7)是：

```systemverilog
XLEN               = 64;
PADDR_WIDTH        = 32;
MEM_AXI_ADDR_WIDTH = 32;
MEM_AXI_DATA_WIDTH = 64;
```

**RV64 不等于已经具备大容量内存寻址能力。** 当前 CPU 物理地址空间最多为 4 GiB，且其中还需要容纳设备映射。它不能直接让 14B INT4 权重完整常驻于 CPU 可寻址内存。

作为功能验证配置，这没有问题；作为最终产品，需要明确更大的物理地址空间，或者加速器独立内存及其访问方式。

带宽同样需要提前计算。假设：

- 使用 7B INT4 稠密模型；
- 单序列、每次生成一个 token；
- 每个 token 约从主存读取一遍权重。

若目标为 20 tokens/s，仅权重读取就约需：

\[
3.5\ \text{GB/token}\times20\ \text{token/s}
=70\ \text{GB/s}
\]

而单个 64 位数据通道，即使假设运行在 1 GHz、每周期传输一个 beat，峰值也只有 8 GB/s。**这是假设条件下的带宽预算，不是当前 RTL 的性能预测。** 如果加速器拥有独立宽接口，就需要按那条实际数据路径重新计算。

这意味着，模型规模、目标吞吐和内存系统必须共同确定，不能只写“完整 AXI4”便认为带宽要求已解决。

软件方面，[当前基线](/home/yong/ysyx/ysyx-workbench/npc/docs/architecture/ARCHITECTURE_PLAN.md:28)明确列出的是 RV64I、CSR、指令同步及机器态异常中断。对于目标 runtime，还需要明确：

- 乘除、原子操作和浮点运算分别如何支持；
- S/U 特权级、MMU、页表遍历和操作系统何时接入；
- 编译器、ABI、推理库和具体模型版本；
- 权重、激活、累加和 KV cache 各自采用什么数值格式。

“INT4 模型”只说明部分数据的表示方式，不能据此认定整个推理流程仅需要低位宽整数计算。

**当前文档的工程方法值得保留，但产品结论仍缺少证据。**

文档已经强调精确提交、接口所有权、分阶段性能计数、同一配置下的 PPA 比较，以及模型不能代替 RTL 验证。这些都直接服务于可靠的架构探索。

不过，[验证记录中的正式性能表](/home/yong/ysyx/ysyx-workbench/npc/docs/verification/EXPERIMENT_LOG.md:81)仍然是“待测”。因此，目前能认可的是研究方向和验证方法，还不能认定这套配置具备面向目标 AI 设备的性能、能效优势。

另有两处文档需要消除歧义：

- [P2 配置计划](/home/yong/ysyx/ysyx-workbench/npc/docs/architecture/P2_CONFIGURATION_PLAN.md:9)仍描述 RV32/RV64 两套配置，与当前唯一 RV64 主线不一致。
- [AXI 拓扑](/home/yong/ysyx/ysyx-workbench/npc/docs/interconnect/AXI4_ARCHITECTURE.md:3)仍只画出 LSU 的 uncached 路径，未体现当前 D-cache 路径。

这些适合标记为历史记录或更新到当前状态。

我建议接下来的顺序是：

1. **固定首个研究场景。** 选择一种设备、一个模型和量化格式，规定上下文长度、并发数、内存容量及功耗口径。
2. **在现有顺序核上尽早运行 AI 相关程序。** 使用文档已经列出的 tokenizer、量化 GEMV、KV 访问和命令队列负载，确定软件能运行以及时间消耗在哪里。
3. **建立最小协同系统。** 先验证 CPU、DMA、一个计算单元和内存之间的提交、数据可见性与完成通知。
4. **根据测量决定扩展顺序。** 若限制来自 CPU 调度和标量执行，再评估乱序；若限制来自计算或访存，则优先处理对应单元和数据路径。
5. **将 3B～14B 保留为系统级目标。** RTL 阶段先验证缩小规模的算子和数据流，完整模型另用软件参考、系统模型或 FPGA 验证，并明确不同验证方式的结论边界。

对你现在的项目，最值得尽早回答的问题是：**在确定的内存与加速器条件下，CPU 的哪些能力实际限制推理性能，增加这些能力需要付出多少面积和能耗？** 这个问题既能支撑 CPU 设计学习，也能让“面向 AI 推理”的定位形成可验证的技术内容。

**可以，完全可以先完成顺序核，再完成乱序核。AI 模型、加速器和最终产品参数，不需要现在全部确定。** 我前面的建议偏向尽早验证产品可行性，对你当前以 CPU 设计学习和实现为主的阶段，要求提得过早了。

关键在于：**“先做顺序，再做乱序”是一条合理的技术路线；至于乱序对具体 AI 负载有多大收益，可以以后验证。** 两件事不必同时完成。

你现在需要明确的是当前 CPU 的设计与验证范围，例如：

- 顺序核支持哪些指令、异常和中断；
- 流水线如何处理相关、反压、分支恢复和精确提交；
- cache、访存和总线接口的行为；
- 顺序核达到什么条件，才进入乱序阶段。

这些会直接影响正在写的 RTL，应该随着实现逐步确定。

而以下内容可以推迟：

- 最终运行哪种 AI 模型、多少参数；
- INT4、INT8 或其他数值格式；
- 向量单元和矩阵加速器的具体结构；
- 最终内存容量、带宽、功耗和 tokens/s 目标。

当前的 32 位物理地址、阻塞式 cache，也可以作为阶段配置保留。**它们限制当前系统能力，但不妨碍你学习和实现乱序执行。** 后续扩展时再处理相应约束即可，不需要现在一次完成。

我支持你按照原来的顺序推进：

1. **完成顺序核。** 把正确性、异常、访存和回归收敛，建立可重复的性能记录。
2. **完成单发射乱序核。** 集中解决重命名、调度、ROB、LSQ、顺序提交和错误恢复。
3. **稳定后评估超标量扩展。** 根据实际执行与访存瓶颈决定扩宽哪些部分。
4. **再引入具体 AI 负载和异构协同。** 用负载判断哪些已有能力有效、哪些还需要补充。

在前两个阶段，用普通程序以及针对相关链、独立运算、分支和访存的测试，就能验证很多核心机制，不必等待完整 AI 软件栈。

**文档现在只需要把目标的确定程度写准确。** 比如：

> 当前目标是完成可验证的 RV64 顺序核，并逐步实现乱序执行和超标量扩展。边缘 AI 推理作为长期应用方向，具体工作负载、异构计算结构和系统指标在后续阶段确定。

这样既保留你的长期方向，也不会让尚未确定的 AI 需求阻碍当前 CPU 开发。前面指出的容量、带宽问题，应当记录为未来系统设计需要解决的问题，不是现在进入乱序阶段的阻断条件。

所以，需要纠正我之前“还没接通”的说法：**缺少的不只是一根连接线，中断产生和 CPU 接受中断的逻辑也没有完成。** 其他几个保存过的 RV32 提交中，中断标志同样固定为零。

正常的定时中断还需要实现：软件设置 `mtimecmp`，计时到期产生请求，CPU 根据中断使能决定是否接受，在指令边界保存返回位置和原因，再跳转到处理入口。

旧版 AM 软件也能印证这个范围：`yield()` 使用 `ecall`，属于同步异常；`ienabled()` 固定返回 `false`，`iset()` 是空函数。因此，RT-Thread 的启动记录不能单独证明已经支持定时器中断或抢占调度。

## 0072 · 助手

**需要补上 CPU 接收中断、选择响应时机，以及进入中断处理程序的逻辑。建议独立一个小的中断控制模块，复用已有的 CSR、异常处理和流水线重定向逻辑。**

下面按你关心的 **RV32I 顺序核版本**说明。

之前检查的 RV32 代码里，CLINT 实现了 `mtime` 计时和读取，但缺少 `mtimecmp` 和中断输出；CPU 也没有接收中断的输入。因此，已有计时功能可以保留，需要把后面的处理流程补完整。

**具体需要改这些地方：**

| 位置 | 需要补充的内容 |
|---|---|
| CLINT | 增加 64 位 `mtimecmp` 及读写接口，通过 `mtime >= mtimecmp` 产生定时器中断请求 |
| 系统顶层、CPU 接口 | 将 CLINT 的中断信号连接到 CPU，例如 `timer_interrupt_i` |
| CSR 模块 | 让 `mip.MTIP` 反映硬件请求；通过 `mie.MTIE`、`mstatus.MIE` 控制是否响应。原先可直接写入的 `mip` 需要按位明确硬件和软件的权限 |
| 中断控制逻辑 | 判断中断是否满足条件，协调流水线停止接收新指令，选择安全的响应时机 |
| 已有异常处理、重定向逻辑 | 接收中断事件，更新异常相关 CSR，清除尚未执行的指令，跳转到处理程序 |
| 软件和验证环境 | 设置定时时间、开关中断、处理中断、重新设置下一次定时，并验证返回和访存行为 |

在当前仅考虑 M-mode 的条件下，定时器中断允许响应的判断可以写成：

```systemverilog
timer_interrupt_enabled =
    timer_interrupt_i && mie_mtie && mstatus_mie;
```

这里表示“允许响应”，实际进入中断还需要满足流水线的安全条件。中断请求即使被屏蔽，仍应能通过 `mip.MTIP` 观察到。[RISC-V 特权规范](https://docs.riscv.org/reference/isa/v20260120/priv/machine.html)

**真正需要仔细设计的是中断与流水线、访存的配合。**

对于我们的单发射顺序核，我建议第一版采用“停止接收新指令，让已经进入执行部分的指令完成，再进入中断”的方案：

1. **发现可响应的中断后，暂停向执行部分送入新指令。** 已经进入执行、访存、写回的指令继续运行，不能把整个流水线一起冻结，否则可能永远等不到完成。
2. **等待已发出的访存及相关操作完成。** 已被 AXI 接收的事务必须正常结束，不能因为中断直接清除事务状态；尤其要保证 store 和 MMIO 不丢失、不重复。
3. **再次检查中断条件，然后进入处理程序。** 等待期间，较老的 CSR 指令可能关闭中断，也可能发生同步异常，因此不能只记住最初的请求就强行进入。

这个方案容易明确指令完成的边界，也不需要增加复杂的回滚结构。代价是中断响应时间会受到未完成访存的影响。

进入定时器中断时，RV32 的关键状态是：

```text
mepc   = 返回后应该执行的指令地址
mcause = 0x80000007
mtval  = 0
```

同时保存、关闭相应的中断使能状态，再跳转到 `mtvec`。**`mepc` 不能直接取当前取指 PC，也不能一律取上一条指令 PC 加 4**，必须考虑已经完成的分支跳转等控制流变化。中断本身也不能算作一条退休指令。[RISC-V 特权规范](https://docs.riscv.org/reference/isa/v20260120/priv/machine.html)

**关于是否单独加模块：建议加，但职责要小。**

可以命名为 `interrupt_controller`，只负责：

- 判断中断请求是否允许响应。
- 协调停止接收新指令和等待已有操作完成。
- 向已有 `trap_controller` 发出中断进入请求。

CSR 状态继续由 `csr_file` 保存，异常入口和 `mret` 继续由现有处理路径负责，避免出现两套状态更新逻辑。

第一阶段先实现 **M-mode 定时器中断**就合适，不需要同时引入 PLIC、多中断源优先级和嵌套中断。软件还要补齐中断开关、定时器处理分支和下一次定时设置；如果用于 RT-Thread，还需要接入时钟节拍。**硬件中断返回地址不能沿用 `ecall` 处理中的 `mepc += 4`。**

验收重点应包括：屏蔽与重新使能、访存等待期间触发、分支后的返回地址、同步异常冲突、`mret` 返回，以及连续定时中断。完成这些后，才适合在简历里明确写“支持 M-mode 定时器中断”。
