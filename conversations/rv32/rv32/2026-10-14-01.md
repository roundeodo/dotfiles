## 1829 · 助手（进度）

2026-10-14 00:05:59.393 UTC

核对 CVA6 源码后，三个接口的含义不同：

- **Branch unit 是组合逻辑，没有独立的 ready 端口**。它接收 ALU 给出的一位比较结果，自己计算目标、检查预测和异常。[源码](https://github.com/openhwgroup/cva6/blob/master/core/branch_unit.sv)
- **LSU 的接收与完成分开**。请求被接收后，还要等待地址转换、缓存或总线；入口缓冲为空时可以组合直通，并非所有请求都必须先存一拍。[源码](https://github.com/openhwgroup/cva6/blob/master/core/lsu_bypass.sv)
- **CSR buffer 保存待提交的 CSR 地址**，直到 commit 或 flush。这是提交上下文，不表示 CSR 计算必须流水化。[源码](https://github.com/openhwgroup/cva6/blob/master/core/csr_buffer.sv)

因此要分别看接收条件、结果延迟、发射间隔和在途容量。当前单级 EX 的 700 MHz 最差路径还经过恢复/反压与 I-cache 替换查询；接下来会把查询候选提前计算，让迟到的握手只选择最终路号。

## 1838 · 助手

2026-10-14 00:29:44.340 UTC

**握手不决定周期数，也不代表内部已经流水化。** 它定义接收条件；结果需要几拍、能否每拍接收新指令，要看内部寄存器、运算结构和资源占用。

我核对了 CVA6 当前源码：

| 单元 | 实际行为 |
|---|---|
| **Branch unit** | 没有独立 ready 端口，是组合逻辑。接收 ALU 的一位条件比较结果，自己计算目标、检查预测和异常。[源码](https://github.com/openhwgroup/cva6/blob/master/core/branch_unit.sv) |
| **LSU** | 请求接收、访问完成、store 提交分别处理。入口 ready 不表示数据已经回来；缓存未命中等情况会延长完成时间。入口缓冲为空时支持组合直通。[源码](https://github.com/openhwgroup/cva6/blob/master/core/lsu_bypass.sv) |
| **CSR buffer** | 保存待提交的 CSR 地址和有效位，直到 commit 或 flush。实际 CSR 操作由提交阶段协调，并将 CSR 读值写回 GPR。[buffer](https://github.com/openhwgroup/cva6/blob/master/core/csr_buffer.sv)、[提交逻辑](https://github.com/openhwgroup/cva6/blob/master/core/commit_stage.sv) |
| **ALU** | 内部是组合运算，但外层共享完成通路仍有 `flu_ready_o`，所以不能说整个 ALU 通路完全没有反压。[源码](https://github.com/openhwgroup/cva6/blob/master/core/ex_stage.sv) |

因此，需要分别检查：**接收至结果可用的延迟、相邻指令的发射间隔、允许多少条在途，以及提交条件。** 仅看 valid/ready，无法确定这些指标。我们当前 LSU 的可变延迟，也不要求普通整数和分支额外经过一级结果寄存器。

## 1848 · 助手

2026-10-14 00:45:01.838 UTC

你记得对：**B/J 早期目标计算仍属于 IFU 的返回处理通路**，由 IFU 实例化组合子模块 `riscv32_direct_target`。它没有时钟、寄存器或独立的 valid/ready，本轮没有把它变成新的流水级。[实例位置](/home/yong/ysyx/ysyx-workbench-rv32-interview/npc/vsrc/riscv32/core/frontend/riscv32_ifu.sv:312)

这里的 B/J 指条件分支和 JAL。条件分支是否真正成立，仍要在 EX 比较 GPR 操作数；IFU 提前得到的是准确目标和预测方向。

原来的目标计算是：

`识别 B/J → 选择位移 → 32 位加法`

现在是：

`B、J 位移分别提取 → 两个目标并行计算 → 按指令类型选择`

每个目标又拆成低 13/21 位加法和高位候选选择，缩短迟到的指令立即数需要经过的进位路径。计算结果没有增加一拍。[目标计算源码](/home/yong/ysyx/ysyx-workbench-rv32-interview/npc/vsrc/riscv32/core/frontend/riscv32_direct_target.sv:20)

**握手协议基本保持原样。变化主要发生在握手之前的组合数据计算，不能把“已经算出结果”当成“已经交付”。** 当前几个边界是：

| 边界 | 什么时候接收 | 接收后做什么 |
|---|---|---|
| IFU → 预测器 | 预测响应槽为空，或旧响应本拍被消费；没有 flush | 在上升沿保存 PC、epoch 和预测结果；允许旧响应出、新查询入同拍进行 |
| 预测响应 → IFU 请求队列 | 队列有空位，或队首本拍被 I-cache 接收 | 空队列可直接送到 I-cache；受阻时保存请求和预测 |
| 请求队列 → I-cache | S1 空闲，或旧本地响应本拍交付；没有 miss/失效占用 | 同沿采样请求身份、读取 tag/data，并保存对应预测 |
| I-cache → IFU → fetch buffer | 当前 epoch 的响应有效，而且 fetch buffer 能接收 | 指令与配对预测一起交付；空 fetch buffer 可以直接通向译码 |

这些转移都以**上升沿的 `valid && ready`**为准。反压期间，请求或响应由原来的寄存器、队列保持。[I-cache 接收条件](/home/yong/ysyx/ysyx-workbench-rv32-interview/npc/vsrc/riscv32/core/frontend/riscv32_icache.sv:120)

例如正常命中、没有恢复时：

- E1 上升沿：I-cache 接收 A，同步读取阵列；IFU 保存 A 对应的预测。
- E1～E2：比较 tag、选出指令字，IFU 组合计算 B/J 目标和预测校验。
- E2 上升沿：下游 ready 时交付 A；同时可以接收下一请求 B。

**B/J 计算就在 E1～E2 之间，没有自己的握手，也不要求再存一拍。**

本轮另外改了四处：

1. **预测后继比较**  
   原来先选择两个宽地址，再比较；现在各地址并行比较，最后选择一位 mismatch。早期恢复仍要求当前指令成功交付：
   ```text
   指令有效 && fetch buffer ready && 无取指错误
   && 目标合法 && 预测后继不一致
   ```
   受阻时可以先算出错误，但不会反复触发恢复。

2. **I-cache 响应选择与预译码数据**  
   PC、epoch、tag 直接使用保持的 S1 身份；命中/miss 数据来源由已有 miss 占用状态选择。新增 `lookup_word_o` 组合线供 IFU 提前计算，**没有独立握手**。公开错误响应仍清零，错误时禁止使用预译码结果恢复 PC。

3. **替换查询前递**  
   用“已经判定命中”和独热命中路提前计算下一请求的 victim。**提前计算不更新 RRPV**：只有真实 hit 交付才更新状态，只有新请求握手才采样 victim。

4. **IFU 的 PC 推进条件**  
   去掉内部重复的恢复门控，但对外请求仍在恢复时禁止发出。逻辑关系是：
   ```text
   if 恢复:
       PC = 恢复地址
   else if 资源允许:
       PC = 正常下一地址
   ```
   在 `else` 中已经确定没有恢复，因此“资源允许”等价于该分支下的真实请求握手，没有绕过协议推进 PC。

请求队列容量、预测响应寄存级、fetch buffer、I-cache 同步读和阻塞回填机制都保持原结构。已经展示且受阻的旧请求也仍须保持到握手，随后按 epoch 排空；恢复不会直接撤销它。

## 1851 · 助手

这两处都要区分：**组合逻辑提前算出候选结果，和时钟沿真正接收请求、更新寄存器，是两件事。**

**第 3 处：重构原有的替换元数据前递。**

假设一个组的四路都有效，RRPV 为：

```text
路号：   0  1  2  3
RRPV：   3  2  1  0
```

RRPV 越大越优先被替换，因此当前候选是路 0。

现在，老请求 A 命中路 0，且满足策略13的提升条件；下一请求 B 要查询同一组。希望在**同一个上升沿**完成：

- A 交付，路 0 的 RRPV 更新为 0。
- B 被接收，为 B 保存替换候选。

B 应当看到更新后的状态：

```text
RRPV：   0  2  1  0
替换候选变为路 1
```

因为两个寄存器在同沿更新，B 不能靠读取“已经写进去的新 RRPV”得到这个结果，所以需要组合前递。

**原来已经有这个前递，但它等待 A 的真实交付条件：**

```text
A 命中 && 下游 ready
        ↓
将路 0 的候选 RRPV 设为 0
        ↓
比较各路，计算 B 的 victim
```

下游 ready 来得晚，后面的比较也跟着晚。

**现在只根据“A 已经命中”提前计算候选。** 真正更新仍受握手控制：

- A 没交付：RRPV 状态不更新。
- B 没被接收：B 的 victim 寄存器不更新。
- B 能被接收时，硬件保证老 A 同拍已经交付，因此采样这个前递结果是正确的。

所以，**提前的是计算，不是状态更新，也不是让 B 绕过阻塞。** 替换决策规则没有改变。[对应源码](/home/yong/ysyx/ysyx-workbench-rv32-interview/npc/vsrc/riscv32/core/frontend/riscv32_icache_replacement.sv:257)

**第 4 处：PC 更新分支里去掉重复条件。**

先定义：

```text
资源允许 = 请求队列可接收
        && 预测查询已启用
        && 预测器 ready

真实请求握手 = 资源允许 && 没有恢复
```

原来的 PC 更新逻辑相当于：

```text
if 有恢复:
    PC = 恢复地址
else if 资源允许 && 没有恢复:
    PC = 正常下一地址
```

进入 `else` 时，已经确定“没有恢复”，因此第二个条件里再次检查它是重复的。现在改成：

```text
if 有恢复:
    PC = 恢复地址
else if 资源允许:
    PC = 正常下一地址
```

**这两个逻辑行为相同。** 有恢复时，始终执行第一个分支；即便“资源允许”为真，也不会执行正常推进。

同时，**对外请求的 valid 仍包含“没有恢复”条件**，恢复拍不会发出普通查询。改动只让内部 PC 推进条件少经过一次恢复门控，并没有取消握手约束。[对应源码](/home/yong/ysyx/ysyx-workbench-rv32-interview/npc/vsrc/riscv32/core/frontend/riscv32_ifu.sv:108)

当前这条 **RV32I 顺序版本**是：**EXU 内的 AGU 计算访存地址，LSU 管理访存请求与完成；分支解析和预测校验也在 EXU 内完成。** 没有启用之前的 scoreboard/ROB 方案。

**地址计算通常属于 EX，MEM 使用已经算好的地址访问存储器。** 经典五级流水线一般复用 ALU 计算：

```text
有效地址 = rs1 的值 + 符号扩展后的立即数
```

我们的地址计算也在 EX，但使用 EXU 内的独立地址运算通路，称为 AGU。地址不经过普通整数 ALU 的结果选择器。

而且，**本轮改动前就已经有这条独立地址通路**。本次只是把原来的普通加法表达式改成“4 位分组进位选择＋前缀进位”，没有新增 AGU 寄存级，也没有单独的 `agu.sv` 模块。[地址计算源码](/home/yong/ysyx/ysyx-workbench-rv32-interview/npc/vsrc/riscv32/core/execute/riscv32_exu.sv:196)

**LSU 接收算好的地址，处理访存语义和握手。** 它主要负责：

- 检查地址对齐，生成 store 数据及字节使能。
- 向 D-cache 或 uncached 通路提交请求。
- 保存当前访存上下文，等待响应。
- 对 load 数据做字节选择、符号扩展，将访问错误转成异常，再交给 WB。

LSU 空闲时，请求可以组合直通到存储层；下游不接收时，才保存请求并重试。它当前只有**一个在途上下文**，属于阻塞式 LSU。[接收与完成条件](/home/yong/ysyx/ysyx-workbench-rv32-interview/npc/vsrc/riscv32/core/memory/riscv32_lsu.sv:278)

**LSU 忙时，会阻止年轻指令继续发射，但不会让整个 CPU 都停止。**

- 年轻独立 ALU、分支指令也要等待，当前不能越过老访存执行并交付。
- 更老的 WB 指令仍可提交。
- 前端可以继续取指、填充已有缓冲；缓冲填满后才逐级反压。
- cache 回填和总线事务继续推进。

老 LSU 成功完成时，它先进入 WB；年轻普通 EX 留在 ID/EX，下一拍才交付。年轻访存则允许在老 LSU **成功完成的同拍**接收；故障时禁止这种交接。这是顺序与精确异常保护的一部分。[阻塞控制](/home/yong/ysyx/ysyx-workbench-rv32-interview/npc/vsrc/riscv32/core/control/riscv32_hazard_ctrl.sv:194)

**之前那一级是普通 EX 结果寄存级，不只是分支预测检验级。** 整数、分支、CSR 结果都经过它，预测校验在它的输出端。

现在变为：

```text
旧：ID/EX → EX计算 → 结果寄存器 → 预测校验 → WB
新：ID/EX → EX计算、分支解析、预测校验 → WB
```

当前没有新增独立的 `branch_unit` 模块。**分支单元的组合电路位于 EXU 内**，完成条件比较、目标计算、对齐检查和预测后继校验。真正恢复前端、训练预测器，仍以结果交付事件为准；受阻时不会提前交付。[分支校验源码](/home/yong/ysyx/ysyx-workbench-rv32-interview/npc/vsrc/riscv32/core/execute/riscv32_exu.sv:252)

我核对了 CVA6 的源码。**它把 branch unit 单独写成模块，是按功能划分电路；并没有因此多加一级流水线，也没有完全脱离 ALU。**

具体分工如下：

| 电路 | 负责什么 |
|---|---|
| ALU 中的比较逻辑 | 判断 `rs1 == rs2`、有符号/无符号大小关系，输出一位“条件成立”信号 |
| Branch unit 的地址逻辑 | 计算 B/J 的 `PC + imm`、JALR 的 `rs1 + imm`，以及顺序地址 `PC + 2/4` |
| Branch unit 的解析逻辑 | 根据条件确定实际方向和恢复地址，检查预测错误，产生目标未对齐异常 |

ALU 的比较结果与整数运算结果是**不同的输出端口**。`ex_stage` 明确把 `alu_branch_res_o` 接到 branch unit 的 `branch_comp_res_i`。所以不是把完整的 ALU 运算结果再送进去，而是传入一位条件判断结果。[ALU 源码](https://github.com/openhwgroup/cva6/blob/master/core/alu.sv#L116-L129)、[实际接线](https://github.com/openhwgroup/cva6/blob/master/core/ex_stage.sv#L320-L367)

以 `BEQ` 为例，同一个 EX 周期里：

1. ALU 判断两个寄存器是否相等。
2. Branch unit **同时**计算 `PC + imm` 和顺序地址。
3. 两路结果汇合，生成实际下一地址及预测纠错信息。

这里不是“先完成整个 ALU，再开始计算跳转目标”。条件比较和目标加法是并行电路，只在最后汇合。还有一个容易误读的地方：`branch_result_o` 输出的是供 JAL/JALR 写入寄存器的**链接地址**，跳转恢复地址在另一个输出结构中。[Branch unit 源码](https://github.com/openhwgroup/cva6/blob/master/core/branch_unit.sv#L54-L107)

**为什么值得单独拆出来？** 从电路组织看，我认为主要是：

- 把 PC、预测信息、控制流恢复和异常处理集中起来，职责清楚。
- 复用 ALU 的比较逻辑，避免重复实现比较器。
- 保留独立目标加法，让它与条件比较并行。

这是我根据源码作出的工程判断。源码可以直接确认的是：**branch unit 没有内部寄存器，没有独立 ready 端口，主体是组合逻辑；`ex_stage` 也明确标注它为组合单元。** 因此，有 `valid` 或被画成单独方框，都不表示它额外占一拍。[执行级源码](https://github.com/openhwgroup/cva6/blob/master/core/ex_stage.sv#L342-L367)

我们当前对应的功能放在 [riscv32_exu.sv](/home/yong/ysyx/ysyx-workbench-rv32-interview/npc/vsrc/riscv32/core/execute/riscv32_exu.sv:127) 内，同样在单级 EX 中完成。**可以参考 CVA6，把分支地址、解析和异常逻辑抽成清楚的组合模块；没有必要因此增加寄存器。** 模块拆分本身也不能保证频率提高。

核对结果已补进 [CVA6 接口记录](/home/yong/ysyx/ysyx-workbench-rv32-interview/npc/docs/verification/data/ex-merge-20261013/cva6-interfaces.md)，本轮没有修改 RTL。

保持 **1 KiB／4 路／32 B 行及相同查询旁路结构**，分段访问 RRIP 相比普通 SRRIP：

- 开发集同频周期减少 **2.66%**。
- 最终保留集按各自合法频率运行，平均时间减少 **0.52%**。
- 最差保留输入慢 **2.13%**。

因此，大幅改善主要来自缓存组织；策略13是在此基础上的小幅优化。其查询旁路还改善了时序，但**旁路前后同频周期不变**，不能算成 IPC 增益。[策略对照](/home/yong/ysyx/ysyx-workbench-rv32-interview/npc/docs/verification/ICACHE_SELECTION_2026-09-21.md:26)

当前采用的**弱态 BTFNT 混合＋早期直接目标**，是在已有 BHT16＋BTB16＋RAS4 上进一步优化：保留短组同频时间减少 **2.64%**；计入合法频率后，短组／长组时间减少 **1.98%／1.42%**。这是额外收益，也不是从无预测开始的收益。[分支最终取舍](/home/yong/ysyx/ysyx-workbench-rv32-interview/npc/docs/research/branch-v3/decision.md:7)

所以，目前能准确说明的是：**基础预测历史计分 IPC 增益约 11%；缓存组织调整收益显著；替换算法及后续预测改进带来较小的额外收益。** 当前单级 EX 版本还没有完成一套“关闭预测／普通替换／最终方案”的同条件 train 消融，不能给出它们在当前 train 上各自的精确贡献。
