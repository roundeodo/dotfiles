## 1324 · 助手

2026-10-01 01:51:35.025 UTC

**是的，已经有特定程序比“不加 ROB、不加 Issue 级”的版本更快；已发射的 LSU/MUL，也不会再让所有后续指令等到它完成。** 但这里有几个明确的条件。

实际整核 RTL 测试结果如下，使用相同的独立仿真存储模型：

| 程序特点 | 原版周期数 | ROB＋Issue 版 | 变化 |
|---|---:|---:|---:|
| 独立 DIV、MUL、ALU、load 混合 | 6649 | 6110 | 减少 **8.11%** |
| load 等待期间执行独立 MUL | 623 | 530 | 减少 **14.93%** |
| 连续独立 MUL | 1076 | 1074 | 基本不变 |
| 连续依赖的 ALU 运算 | 1203 | 1203 | 不变 |

连续 MUL 提升很小，是因为原版就已经支持流水乘法，不能把这项能力归功于 ROB。前两项才直接体现了多个执行单元重叠执行的收益。记录在[验证文档](/home/yong/ysyx/ysyx-workbench-rv32-interview/npc/docs/verification/RV32_RETIRE_BYPASS_2026-10-01.md)。

现在开启 `--backend-rob 1 --load-overlap 1` 时，下面这种情况可以重叠执行：

```asm
lw  t0, 0(a0)      # 已被 LSU 接收，正在等待数据
mul t1, a1, a2     # 无依赖，可以继续发射
add t2, a3, a4     # 无依赖，可以继续发射
```

但**无数据依赖还不够**，还需要目标执行单元可接收、ROB 有空位，并满足访存顺序要求。当前仍然是**顺序发射、允许乱序完成、顺序提交**，有这些限制：

- **LSU 只支持一条在途访存。** 第二条访存如果尚未发射出去，会挡住后面的指令，后面的 MUL 不能越过它。
- **MUL 可以连续接收独立乘法。** DIV 则只能处理一条在途除法，第二条 DIV 也可能挡住后续指令。
- 等待操作数的指令会挡住后面的独立指令，因为现在没有乱序发射队列。
- store、MMIO 等有副作用的操作仍受提交顺序约束；允许提前执行的是符合条件的普通 load。

因此，**执行单元忙，并不一定阻塞整个后端；但顺序发射位置上有一条发不出去的指令，仍会阻塞后续发射。**

也不能据此说所有程序都变快：目前原生 MicroBench `test` 总时间，旧版在合法 680 MHz 下是 **3.193 ms**，新版在合法 700 MHz 下是 **3.223 ms**，尚未取得整体收益。这说明重叠执行能力已经验证有效，但它在这些程序中的收益还不足以完全抵消新增 Issue 级等开销。默认配置目前仍保留 ROB 关闭。

## 1329 · 助手

2026-10-01 01:58:38.238 UTC

**是，CVA6 的 LSU 支持多条在途访存；我们当前只有一条在途访存，确实限制了 ROB 能发挥的作用。** 不过，CVA6 不同 D-cache 配置的并发能力不同，不能统一理解成“所有配置都支持多个 miss 并行”。

这次我核对了 **CVA6 v5.3.0 的实际源码**，主要发现如下。

**Load 的请求发出与结果返回是分开管理的。** CVA6 用 `NrLoadBufEntries` 项 load buffer，保存每条请求的指令身份、地址低位和 load 类型。缓存接收请求后，它可以继续处理下一条 load，无须等所有旧 load 返回；响应携带 ID，再找到对应条目和 scoreboard 指令。前提是有空位、缓存接收，以及地址相关和访问权限等条件满足。[load_unit.sv](https://github.com/openhwgroup/cva6/blob/v5.3.0/core/load_unit.sv)

这里的 buffer 是**保存多条未完成操作所必需的状态**，不是为了分级而额外增加的等待。它解决的是“一条请求等待数据时，硬件还能记住另一条请求”的问题。

**Store 也不是一直占着执行入口等写入完成。** CVA6 分别保存未提交 store 和已提交 store：先计算、保存地址和数据，得到提交授权后再向缓存写入。恢复时取消未提交项，已提交项继续排空。不过，该版本遇到 load 与 store 地址冲突时仍会等待，没有在这个 store buffer 中实现数据前递。[store_buffer.sv](https://github.com/openhwgroup/cva6/blob/v5.3.0/core/store_buffer.sv)

**能否真正重叠 miss，还取决于缓存。**

| 核对的配置/实现 | 实际能力 |
|---|---|
| CVA6 的 `cv32a6_imac_sv32` 配置 | 2 项 load buffer，使用 HPDcache；集成参数推导出 2 项 MSHR |
| HPDcache | 支持同一请求方的多在途请求，以及多个下层未完成读写事务 |
| CVA6 传统 WT D-cache | 读端口进入 `MISS_WAIT` 后停止接收新读，等待该 miss 返回 |

MSHR 保存尚未完成的 cache miss 信息。因此，**两项 load buffer 不自动等于两个并行 miss**，还需要缓存和下层接口配套支持。[RV32 配置](https://github.com/openhwgroup/cva6/blob/v5.3.0/core/include/cv32a6_imac_sv32_config_pkg.sv)、[HPDcache 集成](https://github.com/openhwgroup/cva6/blob/v5.3.0/core/cache_subsystem/cva6_hpdcache_subsystem.sv)、[HPDcache 官方说明](https://github.com/openhwgroup/cv-hpdcache)、[传统 WT 控制器](https://github.com/openhwgroup/cva6/blob/v5.3.0/core/cache_subsystem/wt_dcache_ctrl.sv)

对照我们当前代码，限制实际存在于整条访存通路：

| 位置 | 当前限制 |
|---|---|
| 后端 | 只有一个 `lsu_tag_q`，记录一条访存对应的 ROB 身份 |
| LSU | 只有一份在途上下文 |
| 数据路由 | 当前事务返回后，才能交接下一事务 |
| D-cache | miss 在途时禁止启动新的 lookup |

所以，下面这段程序正好能体现差距：

```asm
lw  t0, 0(a0)       # 第一条 load 正在等待
lw  t1, 0(a1)       # 当前实现无法继续发入 LSU
mul t2, a2, a3      # 即使独立，也不能越过第二条 load
```

我们支持的是“第一条 load 等待时，后面的独立运算可以执行”；**遇到第二条访存，重叠执行就可能停止。** CVA6 配合可接收后续请求的缓存，可以继续接收第二条 load，随后让 MUL 发射，直到遇到真正的依赖或资源限制。

这也是为什么**仅增加 ROB 深度不一定有效**：ROB 有空位，并不能让 LSU 或 D-cache 接收更多请求。另外，我们当前连续 cache hit 已支持旧响应与下一请求同拍交接，因此不能简单归因为“LSU 每次都多等了一拍”。

我认为下一步应优先验证两种收益：

- **解除发射阻塞：** 第二条访存可以被保存，让后面的独立计算继续执行。小型请求队列可能做到，但不代表两个 miss 并行。
- **减少访存等待：** 一个 miss 未完成时继续处理其他 hit；进一步才是两个独立 miss 并行。这需要修改缓存及事务身份管理。

前者改动较小，后者潜在收益更大、面积和验证成本也更高。应分别做对照，不能把收益混在一起。**目前源码已经证明这些限制存在，但还没有测出它们占 MicroBench 总周期的比例，不能直接认定它们就是此前整体变慢的主要原因。**

本次对照、源码来源及后续验证重点已保存到[LSU 研究记录](/home/yong/ysyx/ysyx-workbench-rv32-interview/npc/docs/learning/CVA6_LSU_REVIEW.md)。本轮没有修改 RTL，也没有把源码分析当成仿真验证。

## 1332 · 助手

2026-10-01 02:00:43.083 UTC

**我们的 I-cache 确实在 miss 期间阻塞新取指请求；但刚核对的 CVA6 v5.3.0 I-cache 也如此。** 上一条提到的多在途请求和非阻塞缓存，指的是 **LSU／D-cache**，不能直接套到 I-cache 上。

需要区分两个问题：

| 行为 | 我们当前实现 | 核对的 CVA6 I-cache |
|---|---|---|
| miss 未完成时，继续查询其他取指地址 | 不支持 | 不支持 |
| 同时处理多个取指 miss | 不支持 | 不支持 |
| miss 期间，执行已经取到的指令 | 可以，受依赖和资源约束 | 可以，受依赖和资源约束 |

我们源码中的接收条件明确包含：

```systemverilog
lookup_req_ready_o =
    lookup_s1_ready && !miss_transaction_present && !invalidate_req_i;
```

所以只要 miss 仍在途，即使下一个地址可能命中，也不会启动查询。[本核 I-cache](/home/yong/ysyx/ysyx-workbench-rv32-interview/npc/vsrc/riscv32/core/frontend/riscv32_icache.sv:122)

**但它不会因为 I-cache miss 就冻结整个 CPU。** fetch buffer 中已有的指令可以继续进入后端，已经发射的 MUL、DIV、LSU 也可以继续执行。等已有指令消耗完，前端又没有新指令供应时，发射才会停下来。

我们还实现了 **Early Restart：目标指令字返回后，可以先交给后端执行，剩余 cacheline 继续回填。** 不过，此时唯一的 miss 上下文仍被占用，下一次取指查询仍须等待。因此，“提前返回目标指令”与“回填期间继续查询其他指令”是两种不同能力。

CVA6 的对应源码中，`MISS` 状态保持取指 `ready=0`，等待回填响应后才回到 `IDLE`；即使选择 HPDcache，指令侧仍单独实例化这个 `cva6_icache`。[CVA6 I-cache](https://github.com/openhwgroup/cva6/blob/v5.3.0/core/cache_subsystem/cva6_icache.sv)、[HPDcache 子系统连接](https://github.com/openhwgroup/cva6/blob/v5.3.0/core/cache_subsystem/cva6_hpdcache_subsystem.sv)

所以，如果你说的“miss 后继续执行”是**执行已经取到的指令，我们也支持**；如果是**绕过尚未完成的 I-cache miss，继续取其他地址的指令，这次核对的双方都不支持**。

## 1334 · 助手

2026-10-01 02:02:12.166 UTC

**这个判断方向基本正确，但“LSU／D-cache 限制了并行度”已经有源码依据，“它们是 ROB 整体收益不足的主要原因”还需要测量确认。**

具体应这样理解：

- **I-cache：在刚才比较的能力上接近。** 都是命中可流水处理、miss 阻塞后续查询，后端可以继续执行已有指令。我们还有关键字提前返回。但这不代表缓存容量、取指带宽、缓冲深度等全部相当。
- **LSU／D-cache：当前并发能力确实较弱。** 我们只有一个在途访存，D-cache miss 时不能继续查询其他地址；没有 store buffer。CVA6 配合 HPDcache 的配置，在这些方面更完整。
- **Scoreboard／ROB：已经发挥作用，但能利用的执行机会受限。** Scoreboard 判断依赖并选择前递，ROB 接收乱序完成结果并保证顺序退休；它们本身不能让忙碌的 LSU 接收第二条请求，也不能让年轻指令越过尚未发射的阻塞指令。

例如：

```asm
lw  t0, 0(a0)      # miss
lw  t1, 0(a1)      # LSU 忙，无法发射
mul t2, a2, a3     # 无数据依赖，但被前面的 lw 挡住
```

这时即使 ROB 还有空位，MUL 也不能执行。**因此，只加入 ROB，却保留单事务 LSU 和阻塞 D-cache，确实会限制应用收益。**

不过还有其他因素：程序本身的 RAW 依赖、顺序发射限制、新增 Issue 级带来的延迟，以及分支恢复开销。之前定向程序已经测到约 **8%～15% 的周期下降**，说明重叠执行有效；原生 MicroBench `test` 整体尚未变快，说明这些收益还不足以抵消其他开销。

**下一步应重点统计“第二条访存挡住后续发射”究竟占多少周期，再分别比较小型访存队列、miss 期间继续处理 hit、多个 miss 并行的收益。** 这比继续单独增大 ROB 更有针对性，但最终仍需同时看执行时间、面积和合法频率。

**不会直接变成完整的 CVA6 方案，但会采用它的一部分核心思路：将访存请求的接收与结果返回分开，让多个操作有机会重叠执行。**

而且，CVA6 有不同的缓存配置，不能笼统地认为它们都具有相同的并发能力。

以我们核对的 **CVA6 v5.3.0、`cv32a6_imac_sv32` 配置**为参照：

| 项目 | 我们完成两步升级后的目标 | 该 CVA6 配置 |
|---|---|---|
| LSU 的 load 状态 | 保存两条请求的状态，按身份返回结果 | 两项 load buffer，按响应 ID 找到对应指令 |
| miss 期间处理其他 hit | 支持，但受到端口和地址冲突限制 | 使用非阻塞 HPDcache |
| 同时处理多个 miss | 暂时只允许一个 | 配置为两项 MSHR |
| store 缓冲 | 本轮暂不增加，保留当前提交与错误确认规则 | 区分未提交和已提交的 store 队列 |
| 缓存写策略 | 保留现有 write-back/write-allocate | 该配置选择 HPDCACHE_WT，即 write-through |

配置和 MSHR 数量分别来自官方的[配置文件](https://github.com/openhwgroup/cva6/blob/v5.3.0/core/include/cv32a6_imac_sv32_config_pkg.sv)与[缓存集成源码](https://github.com/openhwgroup/cva6/blob/v5.3.0/core/cache_subsystem/cva6_hpdcache_subsystem.sv)。

**第一步与 CVA6 最接近的是请求与完成解耦。** 不必等第一条 load 返回，才允许接收下一条；每条请求都保留自己的完成身份和取消状态。不过，CVA6 的 load buffer 在缓存接受请求时分配，我们还需要处理“第二条请求已被 LSU 接收，但阻塞式缓存尚未接受”的情况，所以入口控制不能直接照搬。[load_unit 源码](https://github.com/openhwgroup/cva6/blob/v5.3.0/core/load_unit.sv)

**第二步采用的是非阻塞缓存的一部分能力：hit-under-miss。** 第一条 load 等待回填时，第二条 load 如果命中其他可访问的行，就可以先返回；如果也 miss，则仍需等待。它还不具备两条独立 miss 同时访问下层的能力。

另外，CVA6 的 store buffer 将“保存未提交 store”和“提交后向缓存排空”分开。这也是重要的并发来源，但涉及 store 退休后如何处理错误，需要单独设计，不能顺带放开。[store_buffer 源码](https://github.com/openhwgroup/cva6/blob/v5.3.0/core/store_buffer.sv)

因此，这两步应当称为：**参考 CVA6 的访存解耦方式，实现适合本核的两项 load 上下文与单 miss 非阻塞 D-cache。** 它是一个有明确边界的升级候选，还不是最终选型；是否继续加入多 MSHR 和 store buffer，要看升级后的实际收益、剩余瓶颈及面积时序结果。

两步完成后，我们仍然是**顺序发射、允许执行完成乱序、顺序提交**，不会因此变成能够任意越过阻塞指令发射的乱序处理器。

源码中的依据很明确：

- 接口 `dreq_o.ready` 默认是 `0`。
- 命中时，可以拉高 `ready`，接收下一次查询。
- 进入 `MISS` 后，不再拉高 `ready`，等待 `ICACHE_IFILL_ACK` 返回。
- 即使旧请求被分支恢复取消，也会进入 `KILL_MISS`，等待旧响应排空后再恢复查询。[CVA6 I-cache 源码](https://github.com/openhwgroup/cva6/blob/v5.3.0/core/cache_subsystem/cva6_icache.sv)

两者的主要对应关系是：

| 能力 | CVA6 的这个 I-cache | 我们当前 I-cache |
|---|---|---|
| 连续命中时流水接收查询 | 支持 | 支持 |
| miss 未结束时查询其他缓存行 | 不支持 | 不支持 |
| 同时处理多个 miss | 不支持 | 不支持 |
| miss 数据返回方式 | 等待整行回填响应 | 关键字到达即可提前返回，剩余回填继续 |

我们的阻塞条件也直接写在[请求握手逻辑](/home/yong/ysyx/ysyx-workbench-rv32-interview/npc/vsrc/riscv32/core/frontend/riscv32_icache.sv)中：

```systemverilog
lookup_req_ready_o =
    lookup_s1_ready && !miss_transaction_present && !invalidate_req_i;
```

**需要区分“关键字提前返回”和 hit-under-miss。** 我们的 early restart 能让触发 miss 的那条指令提前进入后端，但不能让另一次查询在剩余回填期间访问其他已命中的行。

另外，前面讨论的 **HPDcache 非阻塞能力属于 D-cache**。CVA6 的 HPDcache 集成仍然实例化这个标准 I-cache，并没有同步把 I-cache 改为非阻塞结构。[集成源码](https://github.com/openhwgroup/cva6/blob/v5.3.0/core/cache_subsystem/cva6_hpdcache_subsystem.sv)

因此，如果此前“CVA6 在 I-cache miss 后还能继续执行”让你理解为“还能继续进行新的命中取指”，需要纠正：**已经取到的指令可以继续向后执行，但新的 I-cache 查询仍然会被 miss 阻塞。**

1. **必须整体设计请求的生命周期。** LSU 接收、缓存接收、miss 分配、响应返回和 ROB 完成是不同事件，不能只增加队列深度。
2. **store 路径要从一开始纳入设计。** 包括地址/数据暂存、写入授权、与年轻 load 的相关检查及错误确认。只优化 load，可能很快再次被 store 阻塞。
3. **等待要有明确原因和解除条件。** HPDcache 的条件重试、Rocket 的同行请求管理值得借鉴；它们现有的寄存级和等待周期仍需按我们的阵列、接口和时序重新判断。

接下来的比较范围也扩展为：容量变化、load 接收解耦、hit-under-miss、同行请求处理、多 miss 与互连、小型 store 暂存及转发。验收覆盖 MicroBench，以及已有的 JSON/BPE、量化数据加载、runtime 图控制负载，不能只看几个热点程序。
