Total 用时增加 **1.32%**，Scored 增加 **1.49%**。因此，目前新增后端并发能力还没有在 train 上抵消其整体代价。**不能把这些退化全部归因于双槽，因为期间还加入、修改了 ROB 和 Issue 等结构。**

对于你之前贴过的 ROB 版本前三项，本次几乎不变：

| 子程序 | 之前 ROB 版本 | 本次 |
|---|---:|---:|
| qsort | 39.124 ms | 39.123 ms |
| queen | 13.626 ms | 13.626 ms |
| bf | 29.720 ms | 29.719 ms |

这几项看不出实质提升。严格确认双槽对 **train** 的净收益，还缺少**当前同一份 RTL，关闭双槽和 hit-under-miss** 的完整对照。此前完成的 **test** 对照中，Scored 周期仅减少约 **0.048%**。

**LSU 和 D-cache 具体升级了什么？**

| 部分 | 之前 | 现在开启实验配置后 |
|---|---|---|
| LSU 请求上下文 | 只能保存一条未完成访存 | 最多保存两条未完成访存 |
| 返回身份 | 单请求对应返回 | 每个请求携带 ID，返回匹配相应槽位和 ROB 项 |
| D-cache 正在处理 miss | 后续查询等待 | 无阵列冲突时，允许后续 load 查询并命中返回 |
| 后续 load 也 miss | 等待 | **仍然等待**，没有增加第二个 miss 处理上下文 |
| store、MMIO | 顺序约束 | 仍要求 ROB 队首授权，保持精确异常与副作用顺序 |

例如，这个指令序列：

```text
load A    // miss
load B    // hit，且与 A 没有地址/数据依赖
add       // 依赖 B，不依赖 A
```

旧结构中，第二条 load 等第一条完成才能进入 LSU。新结构允许它进入第二个槽位；D-cache 条件允许时可以先返回 B，使依赖 B 的指令推进。最终仍按 ROB 顺序提交。

**双槽不是双发射，也不是两个 miss 可以同时访问内存。** 当前仍然：

- 单发射、顺序 Issue，不能跳过一条 RAW 阻塞的指令去发射后面的指令。
- 只有一个 miss 上下文，两个 miss 不能并行回填。
- D-cache 仍为 **256 B、2 路、16 B 缓存行**，没有增加容量。
- 没有为这次升级增加新的固定流水级；空槽接收及满足条件的响应交接保留直通。

具体连接和恢复规则见[并发访存设计说明](/home/yong/ysyx/ysyx-workbench-rv32-interview/npc/docs/microarchitecture/LSU_CONCURRENCY_DESIGN.md)。

**为什么这次收益不明显？**

你的结果显示：

- D-cache miss 率约 **19.12%**，平均 miss 响应约 **115 周期**。
- 发射槽统计中，RAW 等待占 **48.49%**，LSU 结构等待占 **22.48%**。
- ROB 队首等待约占总周期 **73.3%**；这个事件与前面的等待分类重叠，不能相加。

双槽主要改善“已有访存未完成，但后续独立 load 可以命中”的情况。它无法消除依赖 miss 数据的等待，也无法让第二个 miss 并行回填。此前 test 已经观察到：**LSU 容量等待减少，但部分等待转移到了 RAW 和 ROB 满，程序总周期几乎没变。**

所以目前应把它定位为**已实现并验证的可选并发能力**，还不能称为已证明有效的 MicroBench 优化。面积增加约 **0.60%**、两种配置均通过 700 MHz，而现有应用收益很小，继续默认关闭是合理的。

## 1409 · 助手

2026-10-01 08:12:35.697 UTC

**还没有做到与 CVA6 的 LSU、D-cache 方案等价。当前实现借鉴了其中部分机制，是适配我们这个小核的裁剪方案。** 如果之前的表述让你以为已经完整实现了 CVA6 的访存系统，那不准确。

另外，CVA6 可以配置不同的缓存实现，比较时必须明确具体版本和配置，不能把它视为唯一固定结构。

我们现在实际具备的是：

| 能力 | 当前实现 |
|---|---|
| 多条访存同时在途 | LSU 最多保存两条请求 |
| 请求与返回匹配 | 使用事务 ID，关联对应 ROB 项 |
| 较年轻 load 先完成 | 满足条件时可以，最终顺序提交 |
| miss 期间处理其他 load 命中 | 支持有限的 hit-under-miss |
| 同时处理多个独立 miss | **不支持**，只有一个 miss 上下文 |
| 已提交 store buffer | **没有**，store 仍等待成功响应后退休 |
| store-to-load forwarding | **没有实现通用的存储队列转发** |
| 未知地址投机、访存违例重放 | **没有** |
| 跳过阻塞指令继续发射 | **不能**，仍是顺序 Issue |

其中，**请求身份与完成解耦参考了 CVA6；D-cache 缺失行预留、查询与 miss 处理分离更多参考了 HPDcache 的思路。** 并不是把 CVA6 的 LSU 和缓存直接搬过来。

与更完整的访存系统相比，我们现在主要还差两方面：

- **store 的执行与退休解耦。** 当前 store 必须在队首获得授权，并等待响应，容易限制后续推进。加入已提交 store buffer 能改变这一点，但必须同时明确写回报错后的处理方式。
- **更多 miss 并发及配套互连能力。** 单纯增加 LSU 槽位无法实现这一点，需要缓存缺失状态、请求身份、返回路由和下层总线一起支持。

所以，准确的定位是：**我们已经从单请求、阻塞式访存，升级为“两条请求在途＋单 miss 下允许 load 命中返回”，但还不是完整的 CVA6 访存方案，也不是完整的非阻塞 D-cache。** 这也解释了为什么双槽确实能工作，却没有让目前的 train 明显变快。

## 1411 · 助手

**对，你说得对。我们讨论的常规 CVA6 也是顺序发射，不能跳过在 Issue 阶段阻塞的指令，去发射后面的独立指令。** 官方文档明确说明：一条指令使 Issue 停顿，后面的指令也会被阻塞。[CVA6 设计文档](https://cva6.readthedocs.io/en/latest/04_cv32a65x/design/design.html)

我上一条把这一点放在“与 CVA6 的差距”的语境里，容易造成误解，应该纠正：**这是两者共有的限制，不是我们相比 CVA6 缺少的能力。**

需要区分两种情况：

```asm
lw   x5, 0(x10)     # 已发射，正在等待返回
add  x6, x7, x8     # 无依赖，资源允许时可以继续发射
```

这里不需要跳过指令。第一条已经离开 Issue，第二条可以正常发射，甚至先完成。

```asm
lw   x5, 0(x10)     # 已发射，正在等待返回
add  x6, x5, x8     # 等待 x5，阻塞在 Issue
add  x9, x11, x12   # 虽然独立，也不能越过第二条发射
```

第二种情况，常规 CVA6 和我们当前的结构都会停顿。**允许已发射指令乱序完成，不等于支持乱序发射。**

因此，后续评估我们的 LSU 升级，应关注请求接收能力、访存缓冲、命中能否越过 miss 返回、store 的处理方式及其实际周期收益；不能用“CVA6 能绕过 Issue 阻塞”来解释差距。

## 1414 · 助手

2026-10-01 08:18:14.035 UTC

**对，常规 CVA6 也不行。它是顺序发射：当前指令因操作数未就绪或功能单元无法接收而阻塞时，后面的独立指令也不能越过它发射。** [官方设计文档](https://cva6.readthedocs.io/en/latest/04_cv32a65x/design/design.html)

区别在于阻塞发生在哪里：

- **较老指令已经发射，在等待完成**：后续独立指令满足条件时可以继续发射，并先完成。
- **当前指令尚未发射，阻塞在 Issue**：后续指令不能跳过它。

所以 CVA6 可以做到**顺序发射、执行重叠、乱序完成、顺序提交**，但这不等于乱序发射。

我之前把“无法跳过阻塞指令”放在我们与 CVA6 的差距里，表述不准确。**这是两者共有的限制，不能据此解释我们的性能差距。** 应当比较的是具体的 LSU 接收能力、store 缓冲、缓存并发和等待条件。
