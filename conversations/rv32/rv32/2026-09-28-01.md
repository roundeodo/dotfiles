## 1059 · 助手

2026-09-28 02:15:55.354 UTC

我核对了手册和当前源码。**手册的目标是正确模拟“高频 CPU 访问低频设备”，当前 APB 的单事务校准思路基本符合这个目标；AXI 虽然分别校准了读写，但并发时的时间归属仍有问题，不能认为已经准确。**

首先要固定一个原则：**设备花费的物理时间不能因为提高 CPU 主频而等比例增加。**

设设备频率为 100 MHz，CPU 频率为 \(F_{\text{CPU}}\)，则：

\[
r=\frac{F_{\text{CPU}}}{100\text{ MHz}}
\]

一个操作若需要 10 个设备周期，其服务时间就是 100 ns；对应 580 MHz CPU 的 58 拍、720 MHz CPU 的 72 拍。这是延迟校准应该实现的效果。

手册要求 APB 按事务区间换算；AXI 从 VALID 首次有效开始，包含握手前等待，读写分别计时，并校准突发传输的每拍数据。因此，**只延迟写响应 B、忽略 W 数据传输，并不满足当前带 D-cache 的需求。**[一生一芯 B4 手册](https://ysyx.oscc.cc/docs/2407/b/4.html)

目前代码实际这样实现：

| 通路 | 当前实现 |
|---|---|
| APB | 从 setup 开始计时；下游完成后保存数据和错误状态，补足延迟，再向上游返回 PREADY |
| AXI 读 | 从 ARVALID 开始计时；保存每个 R beat 及其返回期限，到期后向 CPU 提供 |
| AXI 写 | 分别跟踪 AW、W；每拍 W 被下游接收后，推迟向上游确认；最后按条件返回 B |
| 频率换算 | 使用 CPU/100 MHz 的定点比例，保留小数余量 |

当前 SDRAM 走 AXI 延迟器，APB 外设走 APB 延迟器，**不是同一笔 SDRAM 访问先后被两者缩放。**

APB 这样做的理由比较直接：一笔访问在完成前保持请求，下游完成后，CPU 还需要等待剩余的校准时间。假设下游已经经过 \(k\) 拍，目标总等待约为 \(kr\)，因此补等的是：

\[
\max(kr-k,\ 0)
\]

不能再额外等待完整的 \(kr\)，否则会多算已经经过的时间。当前代码也会在捕获响应后停止向下游展示访问，避免同一次寄存器写或带副作用的读被执行多次。

**在单事务、设备响应区间可以视为未校准设备时间的前提下，这个 APB 方案合理。**但它仍只是事务延迟近似：外设内部状态继续随仿真主时钟运行，推迟 PREADY 并没有真正降低外设时钟。

AXI 的问题在于，上述前提在并发情况下被破坏了：

- W 校准已经插入了一段 CPU 等待。
- SDRAM 仲裁使读请求等待这笔写事务。
- 读计时器又把包含这段等待的整个区间乘以 \(r\)。

**同一段等待被再次放大了。**上一轮复现的“提前发读第 123 拍返回，晚发读却第 50 拍返回”，就是这条路径的结果。

但修复不能简单变成“W 等待时暂停读计数”。设备可能正在同时推进其他工作；也不能改成从 AR 握手后才计时，那会漏掉真实的设备仲裁等待。

我认为后续应采用下面的时间约定：

| 时间来源 | 应怎样处理 |
|---|---|
| SDRAM 命令执行、真实设备仲裁、数据传输 | 按设备时间推进 |
| CPU 尚未准备好下一拍 W 数据 | 按 CPU 时间经过，不再乘倍率 |
| CPU 对 R/B 施加反压 | 按 CPU 时间处理，并保留其对队列占用的影响 |
| 延迟器已经插入的等待 | 不能再次缩放 |
| 读写可以重叠的阶段 | 保留重叠，不能把延迟简单相加 |

**对现在这颗支持写回与回填重叠的 CPU，我建议先建立统一按 100 MHz 推进设备状态的参考模型，再据此修正性能模型。**

具体设置应当是：

1. CPU 使用所测配置通过 STA 的频率。
2. SDRAM 控制器、颗粒及相关设备状态按 100 MHz 推进，刷新计数也属于设备域。
3. CPU 与设备边界明确队列深度、允许的在途事务数和跨域延迟。
4. 如果设备已经按真实的 100 MHz 时序推进，外层延迟器就应旁路或设为 1，不能再次乘频率比。
5. CLINT 与这套统一物理时间保持一致，程序时间和 IPC 仍使用同一统计窗口。

这可以通过独立时钟事件，或经过验证的设备时钟使能实现。**不必因此放弃 Verilator**；它支持由仿真驱动安排时钟变化和求值。[Verilator 官方说明](https://verilator.org/guide/latest/connecting.html)

这比当前仅延迟响应更合理，因为设备内部的仲裁、刷新和请求间隔也处于一致的时间尺度中。当前源码中，SDRAM 刷新计数每个主时钟周期都会递减；只把响应推迟，无法完整模拟设备以 100 MHz 自主运行。

不过，即便如此，也只能说结果对应**我们声明的 SDRAM、控制器和互连模型**。真实芯片还涉及跨时钟域电路、PHY、板级连接等成本。若参考模型暂时使用理想跨域接口，就必须注明，不能宣称已经精确预测硅上时间。

验证时也不能只检查公式或程序 PASS。需要用独立参考检查单次访问、突发读写、CPU 数据空档、反压、并发仲裁和刷新；固定设备服务条件后，比较不同 CPU 频率下以 ns 表示的服务时间。

我已把手册依据、当前实现和后续约定写入[设备延迟模型说明](/home/yong/ysyx/ysyx-workbench-rv32-interview/npc/docs/interconnect/DEVICE_TIMING_MODEL.md)。**本轮完成的是设计复核，尚未修改模型，也没有把现有成绩重新认定为准确的硬件性能。**

**当前默认没有启用 GHR；使用的是“按 PC 索引的两位饱和计数器表”。我们之前探索过 GHR 相关预测，而且已经实现了 gshare、Bi-mode 和小型 TAGE 的 RTL，作为默认关闭的实验选项。**

当前 RV32I 和 RV32IM 使用相同的预测配置：

- **方向预测：16 项、每项 2 bit 的 bimodal 表**，代码中叫 BHT。
- 索引为 `PC[5:2]`，计数器最高位决定条件分支预测方向，实际结果用于饱和增减。
- **BTB：16 项、两路**，提供控制流类型及目标地址。
- **RAS：4 项**，提供返回地址。

关于术语：**GHR 保存最近若干条分支的方向序列；PHT 通常保存用于预测的饱和计数器。**当前 BHT 属于方向计数器表，但没有用全局历史形成索引，所以面试时准确说成“PC 索引的 bimodal 两位计数器预测器”最清楚。[对应 RTL](/home/yong/ysyx/ysyx-workbench-rv32-interview/npc/vsrc/riscv32/core/frontend/riscv32_bht.sv:75)

之前实际探索的范围是：

| 方案 | 使用历史的方式 | 完成程度 |
|---|---|---|
| gshare | PC 索引与 GHR 异或，再查计数器表 | 模型、RTL、整核性能及综合/STA |
| Bi-mode | GHR 参与两张方向表索引，另有 PC 选择表 | 模型、RTL、整核比较 |
| 小型 TAGE | 基础表加历史长度为 4/8/16 的三张带标签表 | 模型、RTL、整核性能及综合/STA |
| 局部历史、感知器、循环预测 | 分别利用单分支历史、加权历史、循环规律 | 模型筛选，未全部实现 RTL |

## 1122 · 助手

**分支预测确实有很多方法。之前我们做过多类探索，但没有把所有先进算法都完整实现；“研究过”“模型测过”“做成 RTL”必须分开说。**

你说的可能是 **BTFNT：Backward Taken, Forward Not Taken**，即后向条件分支预测跳转、前向条件分支预测不跳转。它属于静态预测，不需要学习历史。Ibex 就提供了这种可选机制。[Ibex 官方说明](https://ibex-core.readthedocs.io/en/latest/03_reference/instruction_fetch.html#branch-prediction)

我们之前的覆盖范围是：

| 方法 | 核心思路 | 本项目完成到哪里 |
|---|---|---|
| BTFNT | 按分支偏移方向预测 | 未找到独立的 RTL/PPA 对照记录 |
| Bimodal | PC 索引两位饱和计数器 | 当前默认；比较过不同容量 |
| Gshare | PC 与全局历史异或后查表 | 模型、RTL、性能、综合/STA |
| Bi-mode | 两张方向表配合选择表，减少不同偏向分支的干扰 | 模型、RTL、整核比较 |
| 局部历史预测 | 利用同一分支过去的方向序列 | 模型筛选 |
| 感知器预测 | 对历史位加权求和，学习历史相关性 | 模型筛选，未实现 RTL |
| 循环预测器 | 学习循环迭代次数和退出位置 | 模型筛选，未实现 RTL |
| 小型 TAGE | 多种历史长度、带标签预测表、提供者选择 | 模型、RTL、性能、综合/STA |
| 完整 TAGE-SC-L、Bullseye 等 | 在较强预测器上进一步纠错或专门处理难预测分支 | 文献研究，未完整实现 |

具体记录见[分支研究笔记](/home/yong/ysyx/ysyx-workbench-rv32-interview/npc/docs/learning/BRANCH_RESEARCH_NOTES.md:208)。

更先进的方法当然存在。例如：

- **TAGE-SC-L** 在 TAGE 基础上增加统计纠正器和循环预测器。我们的小型 TAGE 没有实现这两部分，不能称为完整 TAGE-SC-L。[作者论文](https://jilp.org/cbp2016/paper/AndreSeznecLimited.pdf)
- **Bullseye，2025 年作者预印本**，识别难预测分支，再为它们选择专门的感知器。论文是在约 159 KB 的 TAGE-SC-L 上增加约 28 KB 子系统；我们只研究过其思想，没有实现完整的识别、试用和选择机制。[作者论文](https://arxiv.org/abs/2506.06773)

所以，之前的结论应限定为：**在已实现、已验证的候选和当时的 RV32I 负载下，简单 BHT 的面积×执行时间更合适。**不能扩大成“先进预测没有用”或“已经找到了所有方案中的最优解”。尤其推测 GHR、完整统计纠正器等方向，仍没有完成 RTL 探索。

至于 **I-cache：当前命中路径是流水线化的，但 miss 路径仍是阻塞式。**

实际结构是：

| 阶段 | 做什么 |
|---|---|
| S0：输入与阵列读取 | 接收地址、进行 PMA 分类，并行读取各路 tag 和目标指令字 |
| S0→S1 寄存边界 | 同时保存请求身份、属性以及 tag/data 读出结果 |
| S1：命中判断与响应 | 比较各路 tag、选择命中数据，组合产生响应；没有额外 S2 寄存级 |

因此，在连续命中且下游不反压时：

- **请求握手到响应握手为一个周期。**
- **可以每周期接收一个请求、返回一条指令。**
- 当前请求返回的同一个时钟沿，可以接收下一条请求。
- 请求身份和 tag/data 寄存器处于**同一个边界、并行工作**，不是各自再增加一拍。[对应源码](/home/yong/ysyx/ysyx-workbench-rv32-interview/npc/vsrc/riscv32/core/frontend/riscv32_icache.sv:78)

但发生 miss 后，只有一个缺失事务上下文，回填期间不接受新查询。关键指令字可以提前返回，让后端提前执行；**这不代表支持 miss 尚未结束时继续处理其他命中请求，即没有 hit-under-miss。**[I-cache 结构说明](/home/yong/ysyx/ysyx-workbench-rv32-interview/npc/docs/microarchitecture/ICACHE_DESIGN_RECORD.md)
