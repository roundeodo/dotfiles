## 1741 · 助手

2026-10-11 07:43:07.035 UTC

**目前我们报告整核面积和频率时，STA 的边界是“CPU 核＋复位控制器”，不是整个 SoC，也不是整个 NPC 系统。**

我核对了最近的综合命令：使用 `sta-reset`，顶层是 [`riscv32_core_reset_boundary`](/home/yong/ysyx/ysyx-workbench-rv32-baseline-replay/npc/vsrc/riscv32/system/riscv32_core_reset_boundary.sv:1)。这个顶层只实例化复位控制器和 `riscv32_core`。

具体范围如下：

| 电路 | 是否包含 |
|---|---|
| IFU、fetch buffer、译码、寄存器堆、EX、LSU、WB、提交 | 包含 |
| 前递、冒险、异常、中断控制、FENCE.I 控制 | 包含 |
| I-cache及其 tag/data 阵列、回填和 AXI 适配 | 包含 |
| D-cache、分支预测器 | 按该次配置；关闭后不计入有效硬件 |
| 核内数据访问路由、uncached AXI 适配 | 包含 |
| 复位控制器及后来添加的复位缓冲树 | 包含 |
| 核外的取指/访存 AXI 仲裁、本地地址路由 | **不包含** |
| CLINT 定时器 | **不包含**，定时中断作为输入端口 |
| ysyxSoC 总线、APB 桥、UART、存储控制器及外部存储器 | **不包含** |
| 仿真器、性能监视器、软件延迟模型 | **不包含** |

因此，**边界停在 CPU 核的两组 AXI 接口：取指 AXI 和数据 AXI。** STA 会检查核内寄存器之间的路径，以及核内逻辑到这些端口、这些端口到核内寄存器的路径，但不会继续穿过外部仲裁器、SoC 总线和存储控制器。

外部接口怎样计入时序？当前 [SDC 约束](/home/yong/ysyx/ysyx-workbench-rv32-baseline-replay/npc/constr/riscv32_core_reset_boundary.sdc:3)设置：

- 一个 `core_clock`，周期由目标频率决定。
- 数据输入、输出延迟均为 **周期的 20%**。例如 700 MHz 下，周期约 1.429 ns，接口延迟约 0.286 ns。
- 输入转换时间为 0.1 ns。
- 原始异步复位不当作同步数据输入；复位控制器同步释放到核内的时序仍保留检查。

这里的接口延迟是**给外部电路预留的时序预算**，没有综合外部电路来证明它实际满足这个预算。仿真中的 SDRAM/APB 等待几十拍，也不会作为几十拍组合延迟进入这份 STA。

此外，最近实际使用的是 **Yosys 综合＋NanGate45 典型角库＋iEDA/iSTA**。这是**综合后的标准单元网表时序估算**，没有布局布线和提取后的真实连线寄生；缓存阵列也映射成标准单元，而不是 SRAM 宏。

所以，“通过 700 MHz STA”的准确含义是：**对应配置的 CPU 核及复位边界，在这套库和约束下通过综合后时序检查。** 它不能说明整个 SoC 或最终布局布线后的芯片都能运行到 700 MHz。上一轮 1 KiB 无预测实验只做了仿真，尚未重新取得这份时序结果。

## 1744 · 助手

2026-10-11 14:54:11.345 UTC

**要验证“按设计的周期和旁路工作”，需要逐周期自动检查。波形用于解释问题；NEMU DiffTest 和程序跑通，都不能单独证明模块没有多等一拍。**

我在设计时应该把三个问题分别验证：结果是否正确、周期行为是否符合约定、这种行为是否带来了实际收益。

**首先，把“两拍完成”写成明确的接口要求。**

必须说明从哪里开始、到哪里结束，以及什么条件下成立。例如：

> 输入请求在 E0 上升沿握手；下游持续允许接收、没有 flush 时，要求输出在 E2 上升沿握手。

测试记录请求身份及输入握手周期，之后检查对应输出：

```text
输出身份、数据必须正确
输出握手周期 − 输入握手周期必须等于 2
不能提前、迟到、丢失或重复
```

还要区分两个时间：

- **结果可用时间**：模块第一次给出正确的 `output_valid`。
- **结果交付时间**：下游通过 `output_valid && output_ready` 接收结果。

下游反压可能延后交付，但不能据此掩盖模块自身多等了一拍。流水化模块还要单独检查吞吐：**延迟两拍，并不意味着每两拍才能接收一条请求。**

**其次，旁路必须检查“当拍发生”，不能只检查最终数据。**

例如，空缓冲允许直通时，测试应检查：

1. 满足旁路条件后，**下一个时钟沿到来之前**，输出已经呈现正确的 valid、数据和身份。
2. 下游 ready 时，当拍能够握手。
3. 下游不 ready 时，数据被正确保存，之后持续稳定。
4. 旧项出队和新项入队同拍发生时，没有插入额外空拍。
5. flush、异常和错误响应出现时，按规定撤销或排空，不能错误直通。

如果只检查“最后读到了正确数据”，旁路被错误写成先存一拍再输出，测试仍可能通过。因此断言必须约束**出现时间**。

仓库里已经有这种检查。例如：

- [I-cache 测试](/home/yong/ysyx/ysyx-workbench-rv32-baseline-replay/npc/tests/rtl/riscv32_icache_contract_tb.sv:90)：下级呈现关键字后，在下一个上升沿之前检查响应是否直接出现，同时核对地址、epoch、tag、数据和错误。
- [AXI 交接测试](/home/yong/ysyx/ysyx-workbench-rv32-baseline-replay/npc/tests/rtl/riscv32_axi4_handoff_tb.sv:56)：旧响应可以接收的当拍，检查新地址是否已经呈现，避免事务之间多一个空闲周期。
- [预测器参考测试](/home/yong/ysyx/ysyx-workbench-rv32-baseline-replay/npc/tests/rtl/riscv32_replay_predictor_tb.sv:190)：逐拍比较 ready、valid、响应身份和预测结果，能发现响应多打一拍、少打一拍或者反压时被替换。

这些参考检查应根据**接口约定**编写，而不是照抄 RTL 状态机，否则实现和测试可能一起多等一拍。

**然后，检查测试是否真的触发了目标情况。**

断言通过还不够：如果旁路条件一次都没出现，它也可以通过。因此要统计或覆盖：

- 有多少次旁路机会，实际直通多少次；
- 连续请求是否达到预期接收间隔；
- 最后一拍响应与下一请求同拍是否出现；
- 随机反压、恢复与响应同拍等边界是否被触发。

预期必须出现的场景没有覆盖，测试就不能算完成。仿真时也要明确启用断言；最近的 replay 单元测试使用了 Verilator 的 `--assert`。

**最后，确认局部效率有没有转化为整核收益。**

模块确实少等一拍，并不保证程序一定更快：当时可能没有下一条请求，也可能仍被别的资源阻塞。需要继续检查整核中的触发次数、停顿周期、工作负载总周期，并结合面积和 STA 判断取舍。旁路省了周期，却拉长组合路径、降低合法频率，也可能得不偿失。

波形在这里用于定位失败：查看请求握手、状态、valid/ready、旁路选择和响应身份，解释是哪条路径多等了。**自动测试负责持续判断，波形负责追查原因。**

坦诚地说，之前已经做了不少逐拍参考、同拍旁路和反压检查，**但我不能声称所有模块的全部延迟、吞吐和旁路要求都已经系统覆盖**。上一轮 MicroBench 扩容测试，也只证明那两组配置的软件结果和测量通过，不能证明每个模块都没有冗余周期。

一个模块完整的效率验收，应当留下：**周期约定、逐拍检查、目标场景覆盖、实际负载收益，以及面积和时序代价**。缺少哪项，就明确标为尚未验证。
