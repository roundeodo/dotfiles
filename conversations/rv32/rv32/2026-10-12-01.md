**可以，你提出的“上升沿 staging → 下降沿 FF 写阵列 → 下一上升沿读出”是可实现的。现在使用低电平 latch，主要考虑标准单元阵列的面积，并不是只有 latch 才能支持读写并行。**

我核对了 replay 和正式 RV32，两边的 [data array](/home/yong/ysyx/ysyx-workbench-rv32-interview/npc/vsrc/riscv32/core/frontend/riscv32_icache_data_array.sv:38) 完全相同。

**先看写入、读出的实际时刻。** 假设 refill 的一个数据字 W 在 E0 上升沿被接受：

| 时刻 | 当前低电平 latch | 你提出的下降沿 FF |
|---|---|---|
| E0 上升沿 | W 进入 staging；若此沿同址读，读到旧数据 | 相同 |
| E0 后的下降沿及低电平阶段 | latch 打开，将 staging 的 W 写入阵列 | 下降沿采样 staging，将 W 写入阵列 |
| E1 上升沿 | 同址读可以读到 W | 同址读也可以读到 W |

因此，**下一上升沿读到刚写入的数据，两种方案都能做到。**

但如果你说的“当拍 lookup”是指 **E0 上升沿同时接受 refill 和 lookup**，那么这个 lookup 的读寄存器已经在 E0 采样；写阵列发生在后面的下降沿，不能改变已经采样的结果。要让它拿到这次 refill 的新数据，需要同址判断和 refill 数据旁路。当前 miss unit 已经通过直接转发关键字，让原始 miss 请求提前获得指令。

**为什么当时选 latch？**

源码记录的目标是减少小容量缓存使用标准单元实现时的面积。我也核对了当前 NanGate45 库：

| 裸存储单元 | 面积 |
|---|---:|
| `DLH_X1` / `DLL_X1` latch | 2.660 µm² |
| `DFF_X1` FF | 4.522 µm² |

阵列有几千位，单个存储位的差别会累积。但这张表不包含写使能、译码、读选择和时钟外围，**不能直接当作整个阵列或整核的面积收益；当前没有这两种实现的完整 A/B 测量。**

下降沿 FF 还有一个时序取舍：它把路径明确分成两段半周期路径：

- 上升沿 staging → 下降沿阵列 FF；
- 下降沿阵列 FF → 上升沿读寄存器。

700 MHz、理想 50% 占空比时，每段只有约 **0.714 ns**，还要扣除相关时序开销。低电平 latch 在整个低电平期间透明，数据可以在下降沿之后继续到达，但仍必须及时经过阵列和读选择逻辑，满足下一上升沿的采样要求。它也需要严格的 latch 时序检查，不能认为天然更快。

**至于 refill 和 lookup 并行，当前真正阻止它的是缓存控制。**

两种阵列组织在电路层面都可以安排读写交叠，但当前 I-cache 明确规定：

```systemverilog
lookup_req_ready_o =
    lookup_s1_ready && !miss_transaction_present && !invalidate_req_i;
```

也就是说，**有 miss/refill 在途时，整个缓存拒绝新 lookup。换成下降沿 FF，不会自动解除这个限制。**

如果要允许回填期间继续命中其他缓存行，还要处理：

- 正在覆盖的 victim 行不能继续被当作有效旧行；
- 正在回填的新行不能因部分数据到达就被当作完整有效行；
- 同址数据、tag 和有效位的读写关系必须一致；
- 原 miss 的关键字响应与新 lookup 的命中响应不能争用输出、混淆身份；
- 新 lookup 再次 miss 时，需要等待或另行分配事务资源。

所以，你提出的存储实现是合理候选；但**改善并行访问，需要修改缓存的查询和回填协议。保留 latch 也可以做这项升级，不必先换 FF。** 这轮我只核对了结构，没有修改 RTL。

例如，假设最后一个 refill beat 在 E1 握手，原 miss 的响应也已消费：

| 时刻 | 当前电路的行为 |
|---|---|
| E1 上升沿 | refill 数据进入 staging；安装新 tag 和有效位；释放 miss |
| E1—E2 | 请求 FIFO 呈现 B；下降沿后 latch 将 staging 数据写入阵列 |
| E2 上升沿 | 接受 B，同时采样 B 的地址、tag、有效位和阵列数据 |
| E2 之后 | S1 按 B 的身份判断命中，使用刚写入的新数据 |

**这个场景当前实现已经能够成立，不需要因为数据更新而让 B 再走一次 miss。**

这里还有两点需要讲准确。

第一，**E1—E2 期间读出寄存器仍保留旧值，不意味着 B 已经被判为 miss。** 当前请求身份和阵列读结果在 E2 同沿采样；E2 之前，旧读出值属于此前的请求，不能拿它当作 B 的结果。你的关键点正是“在 E2 采样前更新阵列”，这一点是对的。

第二，**命中由 tag 和有效位决定，不由 data 新旧决定。** 如果 tag 已命中但 data 错误地读到了旧值，危险是返回错误指令，不是自动转成 miss。因此数据、tag、有效位必须一起对齐。

不过，“refill 回来了”还要区分是否已经进入 staging：

- **E1 已经采样进 staging：**上述过程成立，E2 可以读到新数据。
- **E1 之后才到达，直到 E2 才被采样：**当前 staging 是上升沿 FF，在 E1—E2 之间还没有这份新数据，不能在中间下降沿把它写入阵列。若仍要让 B 在 E2 读到它，就需要从当拍 refill 输入直接旁路到读寄存器输入，并处理对应的 tag/有效位。

所以，**你提出的半周期写入、下一上升沿读取是合理的，当前 latch 组织本来就在利用这个时序。** 真正要进一步讨论的是：能否让“E2 才接受的新 refill”也直接供给“E2 接受的 B”，以及能否在回填尚未结束时继续接受 B；这才涉及新增旁路和缓存控制的修改。

## 1756 · 助手

2026-10-12 04:08:15.649 UTC

**正常情况下：最后一个 refill beat 在 E1 上升沿被接收，E1 之后 I-cache 就可以拉高 `lookup_req_ready`；请求 B 可以在 E1—E2 期间呈现，并在 E2 上升沿被正式接收。不需要等到 E2 之后才开放入口。**

但“数据进入 staging”本身不代表整次 refill 完成。当前结束条件是：

- **最后一个 beat 握手**：`refill_resp_valid && refill_resp_ready && last_word`。
- **原 miss 的响应已经被接收**，没有尚待交付的响应。

满足这两点，miss unit 在该上升沿直接进入 `MISS_IDLE`；否则进入 `MISS_COMPLETE`，继续等待旧响应被接收。

以**最后一个 beat 在 E1 握手、没有错误、旧响应已消费、没有维护请求**为例：

| 时刻 | 发生什么 |
|---|---|
| E0—E1 | 最后一个 refill beat 呈现；miss 仍在途，`lookup_req_ready=0` |
| **E1 上升沿** | 接收最后一个 beat；数据进入 staging，安装 tag/有效位，miss 状态更新为空闲 |
| **E1 之后** | 组合逻辑稳定后，`lookup_req_ready=1`；B 可以呈现地址和 `request_valid` |
| E1—E2 的低电平阶段 | staging 数据写入 latch 阵列 |
| **E2 上升沿** | 若 B 的 `valid && ready`，正式接收 B，同时采样 B 的身份、tag 和新数据 |
| **E2 之后** | S1 的请求有效位为 1，开始对 B 判断命中并产生响应 |

这里必须区分三个信号：

- **`lookup_req_valid`**：由 IFU／请求 FIFO 产生。B 可能早就排在队首，在 refill 期间一直保持 valid。
- **`lookup_req_ready`**：由 I-cache 产生。上述条件下，**E1 之后拉高**。
- **S1 的有效位**：说明 B 已被缓存接收。它在 **E2 上升沿之后拉高**。

所以，“E1—E2 能进来”和“E2 才进来”分别指两个不同动作：**E1—E2 可以展示请求并准备读地址，E2 上升沿才发生接收和采样。** E1 上升沿之前 ready 仍是 0，因此不能把 B 算作已经在 E1 被接收。

如果最后一个 beat 在 E1 被接收，但旧响应仍受反压，入口就不会立即开放。例如旧响应到 E2 才被接收，那么 **E2 之后 ready 拉高，B 最早在 E3 上升沿被接收**。当前设计在这种情况下没有“旧响应消费与新 lookup 同沿接收”的旁路。

另外，原 miss 的关键字响应可以直接从 refill 输入转发，不必等 staging 写入阵列；**关键字可用、整行回填结束、下一请求被接收，是三个不同的事件。**

**是，request FIFO 的队首请求通过组合逻辑直接送到 I-cache，中间没有额外的请求寄存级。** 但不是握手拉高后才开始输出请求。

## 1763 · 助手

2026-10-12 04:18:14.491 UTC

**源码里的行为是：最后一个 refill beat 在 E1 上升沿被接收，B 不能也在 E1 被接收；但 E1 之后入口就可以开放，B 最早在 E2 上升沿被接收。没有额外等待到 E2 之后才开放。**

下面按当前讨论的 baseline replay 源码说明。正式 interview 中的 data array、miss unit 和 refill AXI adapter 与它相同。

**1. Request FIFO 保存请求，不保存指令数据。**

IFU 中有两项请求队列，保存地址、epoch、frontend tag，以及配套预测信息。

[队首输出逻辑](/home/yong/ysyx/ysyx-workbench-rv32-baseline-replay/npc/vsrc/riscv32/core/frontend/riscv32_ifu.sv:159)是组合逻辑：

```systemverilog
assign icache_lookup_req_o = lookup_queue_front_request;
assign icache_lookup_request_handshake =
    icache_lookup_req_valid_o && icache_lookup_req_ready_i;
```

FIFO 非空时，队首 B 可以一直呈现在接口上，即使 I-cache 的 ready 为 0。**只有上升沿采样到 `valid && ready`，才真正接收 B，并推进 FIFO 指针。**

空 FIFO 还允许预测响应直接呈现给 I-cache，不强制先存入队列再等一拍。

**2. 接收请求时，S1 身份和阵列读结果同时采样。**

[I-cache 入口](/home/yong/ysyx/ysyx-workbench-rv32-baseline-replay/npc/vsrc/riscv32/core/frontend/riscv32_icache.sv:105)规定：

```systemverilog
assign lookup_req_ready_o =
    lookup_s1_ready && !miss_transaction_present && !invalidate_req_i;

assign array_read_enable = lookup_req_handshake;
```

在接收 B 的那个上升沿，三组寄存器**并行更新**：

| 寄存器 | 保存内容 |
|---|---|
| `lookup_s1_q` 等 | B 的地址、epoch、tag、访问属性及 S1 占用状态 |
| tag array 的读寄存器 | B 对应各路的 tag 和行有效位 |
| `read_word_data_array_q` | B 对应各路的指令字 |

**它们共同构成查询的 S1 边界，不是串联的三拍。** 我前面说“S1 寄存器输出数据”不够精确：请求信息在 `lookup_s1_q`，指令数据在 data array 的读寄存器，二者同沿对齐。

沿后组合比较 tag 和有效位，命中就选择对应指令字；没有再加一个固定 S2 寄存级。

**3. 请求 A 发生 miss 后，后续 B 留在 FIFO。**

A 在 S1 被判为 miss 后，下一上升沿将 A 的身份和替换位置交给 miss unit，并清除 S1 占用位。

miss unit 在等待回填期间输出：

```systemverilog
miss_transaction_present_o = (state_q != MISS_IDLE);
```

所以 I-cache 的 `lookup_req_ready` 保持 0。B 可以已经呈现，但不能被接收，阵列读寄存器也不会为 B 更新。

这就是当前的 blocking：**关键指令即使提前返回了，剩余 refill 没结束，仍不接受年轻查询。**

**4. Refill 数据写入路径与查询读出路径是分开的。**

每个正常 refill beat 的写入顺序是：

> refill 输入 → 上升沿 staging → 随后的低电平 latch 阵列写入。

[data array 源码](/home/yong/ysyx/ysyx-workbench-rv32-baseline-replay/npc/vsrc/riscv32/core/frontend/riscv32_icache_data_array.sv:77)里，staging 保存的是**一个 beat 的数据和写地址**；它不是额外的 lookup 流水级。

同时，原请求 A 的关键字可以由 miss unit **直接从 refill 输入返回 IFU**，不必经过 staging、阵列，再重新读取。下游反压时才将这个响应保存到响应缓冲。

因此，“A 获得指令”和“整行回填完成”可能发生在不同周期。

**5. 最后一个 beat 与下一次 lookup 的准确交接如下。**

假设最后一个 beat 在 **E1** 握手，整次回填无错误，A 的响应已经消费，B 已在队首，没有维护或恢复干扰：

| 时刻 | Request FIFO／查询侧 | Refill／存储侧 |
|---|---|---|
| **E0—E1** | B 已呈现，valid 可以为 1；ready 为 0 | 最后一个 beat 呈现，miss 状态仍是 `MISS_RECEIVE_REFILL` |
| **E1 上升沿** | **不能接收 B**，因为此沿之前 ready 仍为 0 | 最后一个 beat 进入 staging；安装 tag/有效位；状态更新为 `MISS_IDLE` |
| **E1 之后** | ready 经组合逻辑变为 1；B 驱动读地址 | staging 已保存最后一个数据字 |
| **E1—E2 的低电平阶段** | B 的请求保持稳定 | latch 将最后一个字写入阵列 |
| **E2 上升沿** | **接收 B、FIFO 出队；同时采样 S1 身份和 tag/data** | 最后一个字已经写入，B 可以读到新数据 |
| **E2 之后** | 对 B 判断命中，呈现响应 | 回填事务已经结束 |
| **E3 上升沿** | 若响应 ready，交付 B 的命中响应 | — |

决定结束状态的[代码](/home/yong/ysyx/ysyx-workbench-rv32-baseline-replay/npc/vsrc/riscv32/core/frontend/riscv32_icache_miss_unit.sv:318)位于 refill 握手条件内部：

```systemverilog
if (refill_resp_i.last_word) begin
  state_d = lookup_resp_present_d ? MISS_COMPLETE : MISS_IDLE;
end
```

**如果 A 的响应仍受反压，最后一个 beat 虽然已经收完，状态仍进入 `MISS_COMPLETE`，ready 不开放。** 等 A 的响应在某个上升沿被消费后，状态才变为空闲；下一请求再于后一个上升沿接收。

所以，我之前“最后一拍不允许新 request 进来”的准确意思是：**不允许最后一个 beat 与新 lookup 在同一个上升沿一起握手。** 它不意味着最后一个 beat 接收后，还必须另外空等一整拍才拉高 ready。

若要让 B 也在 E1 被接收，就需要增加最后一拍交接逻辑，并处理数据、tag、有效位的同沿旁路。当前没有这条路径；当前依靠 **E1 写 staging、低电平写阵列、E2 读出**保证对齐。

**基本对，但“B 被接收”发生在 E2 上升沿；命中结果则是在 E2 沿后由组合逻辑产生。**

具体顺序是：

1. **E1 之后**：miss unit 进入 IDLE，I-cache 的 ready 拉高。FIFO 仍输出 B，`valid && ready` 成立。这只是准备好了握手，**FIFO 此时还没有出队 B**。
2. **E2 上升沿**：正式接收 B。FIFO 更新读指针；I-cache 同时采样 B 的请求信息、tag、有效位和 data。
3. **E2 上升沿之后**：假设 FIFO 中 B 后面已有 C，队首输出变为 C；S1 请求寄存器和阵列读寄存器输出 B 的对应信息。
4. **随后组合逻辑稳定**：用 B 的地址与读出的 tag、有效位比较，得到 B 的命中结果，并选择对应指令数据。

因此，**E2 之后，FIFO 输出 C，而 I-cache 的 S1 正在处理 B。**

S1 寄存器本身保存请求信息，**没有单独保存一个“B 命中”的寄存结果**；命中判断在这些寄存器之后组合完成，不需要再等 E3 才判断。

**是，按你现在的定义，你描述的这段交叠过程，当前硬件已经支持。**

正常无错误、没有其他阻塞时：

- **E1 后**：最后一个 refill beat 已进入 staging，staging 输出新数据；miss unit 进入 IDLE，ready 拉高。
- **E1—E2**：请求 B 通过组合路径到达 S1 和阵列读寄存器的输入；与此同时，低电平 latch 把 staging 的新数据写入阵列。
- **E2 后**：寄存器输出 B 的请求信息，以及对应的最新数据；若 B 访问刚回填的行，就可以正常命中。

**但不能把“staging 有输出”单独作为 refill 完成条件。** 每个中间 beat 都会进入 staging、产生输出，此时回填还没结束。

当前开放下一请求的准确条件是：**最后一个 beat 已经接收，且原 miss 没有尚待交付的响应**。满足后，就允许下一请求走组合读路径；不需要等最后一个数据字写完阵列，再额外等一拍开放入口。

所以，你关心的“staging 输出最后一个数据字，同时准备下一请求，下一上升沿读到新数据”，**当前确实能够做到**。
